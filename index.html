前言：把“学 Node.js”变成“做一个项目”

很多人学 Node.js 的经历是相似的：先看一遍语法，再照着教程敲几个 console.log，然后学 fs、http、Express、数据库。每个知识点单独看都懂，合在一起却不知道从哪下手。等到要做一个完整的应用，面前仍然是一堆散落的积木。

这本书想换一种方式：从第一页开始，你就有一个项目。

项目是一个待办事项应用（Todo App）。它足够小，小到一个人可以在一周内做完；又足够完整，完整到能覆盖 Node.js 后端开发的主干：模块化、异步、文件系统、HTTP、Express、模板引擎、MySQL、错误处理、测试、文档和部署。每学一个知识点，我们就把它放进这个项目里，让它从一行 console.log 长成一个可以运行、可以演示、可以继续扩展的 Web 应用。

这本书来自一门 32 小时的实验课。课程只有 8 次课，每次 4 小时，不可能把 Node.js 的每个角落都讲透。所以课堂上的选择是“以终为始”：用一个期末项目牵引学习，讲到哪个知识点，就把它用到项目里。书稿保留了这条主线，同时补上了课堂上因为时间关系没能展开的部分，比如自动化测试、仓库模式、原子写入和部署。

这本书适合谁

  • 学过 JavaScript 基础，知道变量、函数、数组、对象，但没做过完整后端项目的人。
  • 正在上 Node.js 课程，需要一份跟课程进度对应的项目手册的人。
  • 学过 Express，却说不清“中间件为什么按这个顺序执行”“next(err) 到底去了哪里”的人。
  • 想从“能跑”走到“能交付”，需要补上测试、错误处理、README 和部署的人。

书里不假设你有数据库基础，也不假设你用过 Linux。MySQL 的安装、建库、建表会从零讲起；命令行以 Windows PowerShell 为主，macOS 和 Linux 的差异会单独标注。

三种读法

第一种：从头到尾做一遍。 这是最推荐的读法。每章末尾都有“本章验收”，完成后再进入下一章。最终你会得到和 todo-app/ 目录一致的代码。

第二种：按课程进度读。 如果你正在上 8 次实验课，可以按附录 C 的映射表跳读：第 1–2 次课对应第 1–4 章，第 3–4 次课对应第 5–7 章，第 5–6 次课对应第 8–10 章，第 7–8 次课对应第 11–12 章。

第三种：当项目手册查。 如果你已经会 Node.js，只想找一个可运行的项目骨架，可以直接看第 1 章的设计、第 8 章的 Express 结构、第 10 章的 MySQL 接入和第 12 章的测试与部署，其余章节按需查阅。

书里的项目不是最后才出现的，而是一路“升级”出来的。每一章结束，项目都会达到一个可运行的版本。

关于代码的几点说明

第一，书里的代码使用 CommonJS（require / module.exports），和大多数 Node.js 课程、现有项目保持一致。你会在第 2 章看到它和 ES Module 的区别，第 12 章会讨论什么时候适合迁移到 ESM。

第二，最终项目使用 Express 4.x。Express 5 已经发布，但 4.x 仍然是教学和企业项目中最常见的版本，生态兼容性也最好。书里的中间件、错误处理、路由写法在 Express 5 中大部分仍然适用，差异会在相关章节标注。

第三，为了让项目“零配置可运行”，最终代码默认使用 JSON 文件存储，同时保留 MySQL 实现。你不需要先装数据库才能看到页面；等你学到第 10 章，再通过一个环境变量切换过去。课堂上的 data.js 直接读写 JSON、后来替换成 MySQL 的思路没有变，只是我们多抽了一层仓库接口，让两种实现可以并存、可以测试。

第四，书里的代码和 todo-app/ 目录中的代码保持同步。为了控制篇幅，正文只展示关键片段，完整文件请对照配套项目阅读。凡是正文省略的部分，都会明确写出文件路径。

学习建议

不要复制粘贴。至少把每章的核心代码亲手敲一遍，哪怕照着抄。手敲的过程会让你注意到分号、引号、路径、大小写这些复制时永远不会发现的问题。

不要跳过报错。报错是 Node.js 在和你说话。看懂错误栈的第一行、找到自己代码的文件和行号，是这本书里比任何 API 都重要的能力。

不要等到“学完”才做项目。你现在的水平，足够做出这一章要求的版本。做完，再学下一章。

第 1 章 立项：先把事情想清楚

本章版本：v0.0　本章产出：一页立项书、数据模型、API 草图、项目目录蓝图 本章不写代码。但这一章决定了后面十一章写什么、为什么写。

1.1 为什么是 Todo

如果让每个初学者自由选题，最后大概率会得到三种项目：博客、图书管理、待办事项。它们都很好，因为都具备“增删改查”这条完整的骨架。但如果只选一个作为贯穿全书的例子，Todo 有几个明显的优势。

第一，业务足够熟悉。你不需要花时间理解“什么是文章审核”“什么是图书借阅”，每个人都知道待办事项是什么：写下一件事，做完打勾，不做了删掉。业务越简单，越能把注意力放在技术上。

第二，数据模型足够小，却足够完整。一条待办有 id、标题、完成状态、创建时间。它小到可以在一张表里放下，又完整到能覆盖主键、布尔值、时间戳、排序、筛选、搜索这些数据库基础。

第三，需求可以自然生长。第一版只要能增删改查；第二版可以加筛选、搜索；第三版可以加截止日期、优先级、标签；再往后可以做多用户、登录、提醒。项目不是玩具，它有一条真实的演进路线。

第四，演示效果好。答辩时，打开页面，输入一条待办，点击完成，再删除，整个过程不到三十秒，评委立刻知道你的项目能做什么。相比之下，一个只有接口没有页面的项目，很难在五分钟内讲清楚价值。

所以这本书选择 Todo。不是因为它简单，而是因为它小得可以完整做完，又大得足以装下 Node.js 的主干知识。

1.2 需求：用户到底要什么

做项目最容易犯的错误，是一上来就写代码。写着写着发现字段不够、接口不对、页面没地方放，于是推翻重来。立项阶段不需要写代码，但需要把下面四件事写清楚：谁用、用来干什么、第一版做哪些、不做什么。

用户故事

我们假设只有一种角色：普通用户。不需要登录，不需要多用户隔离，打开页面就是自己的待办列表。这不是偷懒，而是把第一版的范围控制住。多用户涉及认证、授权、会话、数据隔离，任何一个都足够单独写一章。

三条核心用户故事：

  1. 作为用户，我想快速添加一条待办，以便把脑子里的事情记下来。
  2. 作为用户，我想看到所有待办，并能区分哪些没做、哪些做完了。
  3. 作为用户，我想修改或删除一条待办，以便纠正错误或清理列表。

再补三条“有了更好”的故事：

  1. 作为用户，我想按“进行中 / 已完成”筛选，以便专注在当前任务上。
  2. 作为用户，我想按关键词搜索，以便在列表变长后快速找到某一条。
  3. 作为用户，我想在操作失败时看到清楚的提示，而不是一个白屏或一串英文报错。

功能清单与优先级

把需求拆成可验收的功能，并标上优先级。P0 是必须完成，P1 是应该完成，P2 是学有余力再做。

P2 截止日期 可以设置和显示截止日期
P2 优先级 高 / 中 / 低，列表可按优先级排序
P2 多用户 注册、登录、每个人只看到自己的待办

这一版做到 P1 为止。 P2 不是“以后有空再说”的客套话，而是刻意留下的扩展点。第 12 章会告诉你，如果继续做，应该从哪里下手。

明确不做什么

立项书里最容易被忽略、却最能救命的一节，是“不做什么”。

  • 不做注册登录。第一版没有用户概念，所有人共享一份数据。
  • 不做前后端分离。页面由服务端渲染，不引入 React/Vue。
  • 不做实时推送。刷新页面才能看到最新数据，这是可接受的。
  • 不做文件上传、富文本、评论、消息通知。
  • 不做微服务、Docker、Kubernetes。第一版是单进程应用。

把“不做什么”写下来，不是为了限制想象力，而是为了在开发中遇到诱惑时，有一个明确的判断依据：它不在本期范围内，记到 backlog 里，继续做当前任务。

1.3 数据模型：一条待办长什么样

数据模型是项目的骨架。字段设计错了，后面每一层都要跟着改。第一版只设计一个资源：Todo。

字段 类型 约束 说明
id 整数 主键，自增，大于 0 唯一标识
title 字符串 必填，去除首尾空格后 1–255 字符 待办内容
completed 布尔值 默认 false 是否完成
createdAt 时间 创建时自动生成 用于排序和展示
updatedAt 时间 每次修改时更新 用于排查和展示

几个设计决定值得解释。

为什么用自增整数，而不是随机字符串？ 自增整数简单、有序、索引效率高，适合单机数据库。随机 ID（如 UUID）更适合分布式系统，避免多台机器生成重复 ID，但可读性差。第一版用自增整数，等以后真的需要分布式，再换。

为什么同时有 createdAt 和 updatedAt？ createdAt 决定列表默认排序：新创建的排在前面。updatedAt 记录最后一次修改时间，调试时非常有用：你可以一眼看出这条数据是刚被改过，还是很久没动。数据库里对应的列名是 created_at / updated_at，API 返回时转成驼峰。这种“数据库用下划线、JavaScript 用驼峰”的映射，是后端非常常见的做法。

为什么时间用 ISO 字符串？ JavaScript 的 Date 对象在 JSON 序列化时会变成 ISO 8601 字符串，例如 2026-11-13T09:21:07.392Z。它带时区信息（Z 表示 UTC），前端可以直接 new Date(...) 解析，也不会因为服务器时区不同而错乱。数据库里我们存 DATETIME(3)，读取时统一转成 ISO 字符串再返回。

标题的长度限制为什么是 255？ 这来自 MySQL 的 VARCHAR(255)。它足够长，能放下一句话；又足够短，不会让人把一整篇文章塞进标题。校验要在三个地方保持一致：页面输入框的 maxlength="255"、API 的参数校验、数据库的列定义。任何一处放宽，都会出现“页面能提交、数据库报错”的尴尬。

状态怎么表示

completed 在 JavaScript 里是布尔值 true / false。在 MySQL 里，BOOLEAN 实际上是 TINYINT(1) 的别名，存 0 / 1。在 JSON 文件里，它仍然是布尔值。仓库层负责转换，业务层和 API 层永远只看到布尔值。

这就是“分层”的第一个好处：每一层可以用最适合自己的表示，但对外保持同一个契约。

1.4 API 蓝图：前后端之间的合同

API 是前端、Postman、curl、未来的移动端共同依赖的合同。合同一旦定下来，就不应该随便改。第一版设计五个核心接口，再加一个健康检查和一个切换状态的快捷接口。

基础路径：/api/todos

方法 路径 作用 成功状态码
GET /api/health 健康检查 200
GET /api/todos 获取列表 200
GET /api/todos/:id 获取单条 200
POST /api/todos 创建 201
PUT /api/todos/:id 全量/部分更新 200
PATCH /api/todos/:id/toggle 切换完成状态 200
DELETE /api/todos/:id 删除 200

为什么是这些方法

REST 的核心思想是：用名词表示资源，用 HTTP 方法表示动作。

  • GET 只读，不应该改变服务器状态。
  • POST 创建新资源，成功返回 201 Created，并在 Location 响应头里给出新资源的地址。
  • PUT 更新资源。严格意义上的 PUT 是全量替换，但教学项目里常用它做部分更新；如果你要更严谨，可以用 PATCH。本书保留 PUT，同时增加一个 PATCH /:id/toggle 作为“只切换完成状态”的快捷操作。
  • DELETE 删除资源。删除成功返回被删除的对象，方便前端确认；也可以返回 204 No Content，本书选择返回对象。

请求与响应示例

创建一条待办：

错误响应统一成这个形状：

json

}

error 是给人看的消息，code 是给程序判断的稳定标识。只有消息没有 code，前端只能靠字符串匹配，消息一改就崩；只有 code 没有消息，调试时又看不懂。两个都给，是最实用的折中。

状态码约定

状态码 含义 什么时候用
200 OK 查询、更新、删除成功
201 Created 创建成功
400 Bad Request 标题为空、id 不是正整数、JSON 格式错误
404 Not Found 待办不存在、接口不存在
500 Internal Server Error 未预期的服务器错误

1.5 页面蓝图：用户看到什么

API 是给程序用的，页面是给人用的。第一版页面只有一个核心页面：/todos。

页面从上到下分四块：

  1. 标题区：应用名“我的待办”，一句简短说明。
  2. 统计区：全部、进行中、已完成三个数字。
  3. 操作区：新增表单、状态筛选、关键词搜索。
  4. 列表区：每条待办显示标题、创建时间、完成按钮、编辑入口、删除按钮。

页面路由与 API 路由分开：

方法 路径 作用

你可能会问：为什么页面路由不用 PUT / DELETE？因为 HTML 表单原生只支持 GET 和 POST。要在表单里发 PUT / DELETE，要么用 JavaScript 的 fetch，要么用“方法覆盖”的中间件。第一版选择最朴素的方式：表单只发 POST，后端处理完重定向回列表页。 这样不需要写一行前端 JavaScript，也能完成所有操作。

这不是“落后”，而是在正确的阶段选择正确的复杂度。等页面跑通、业务稳定，再考虑用 Ajax 提升体验，那时你才有余力处理前端状态管理、错误提示、加载状态这些新问题。

2.1 Node.js 不是一门新语言

先问一个问题：JavaScript 原本运行在哪里？

答案是浏览器。浏览器里有一个 JavaScript 引擎，Chrome 用的是 V8。V8 负责把 JavaScript 代码编译成机器能执行的指令，再交给操作系统运行。浏览器还提供了 document、window、localStorage 这些“浏览器专属”的能力，所以 JavaScript 在浏览器里能操作页面。

Node.js 做的事情，是把 V8 从浏览器里“拿出来”，装到服务器上，再补上一套服务器需要的能力：读写文件、创建网络服务、访问数据库、处理进程。于是同一门 JavaScript，可以脱离浏览器，在操作系统上运行。

所以：

Node.js 不是一门新语言，而是一个让 JavaScript 运行在服务器端的运行时。

这句话很重要。你不需要重新学一门语法；你需要学的是 JavaScript 在服务器端的“脾气”：它怎么处理异步，怎么组织模块，怎么面对成百上千个并发请求。

四个关键词

讲稿里用四个词概括 Node.js 的特点，我们逐个解释。

事件驱动。 程序不是从头到尾一条线执行，而是注册一堆“当某件事发生时，请调用这个函数”的监听器。有人发来请求，触发 request 事件；文件读完，触发 end 事件；定时器到点，触发回调。事件循环负责在事件发生时把对应的函数放进执行队列。

非阻塞 I/O。 读写文件、访问数据库、发送网络请求，这些操作相对 CPU 计算来说非常慢。Node.js 不会停下来等它们完成，而是把任务交给操作系统或线程池，自己继续处理别的事情。等结果回来，再通过回调通知你。这就是为什么一个单线程的 Node.js 能同时处理大量连接：大部分时间它在等 I/O，而不是算东西。

单线程。 这里说的是 JavaScript 主执行线程只有一个。你写的代码不会被两个线程同时执行，所以不用担心变量被另一个线程改掉。但 Node.js 进程并不是真的只有一个线程：libuv 维护了一个线程池处理文件、DNS 等任务，V8 也有自己的垃圾回收线程。准确的说法是“单主线程 + 事件循环 + 后台线程池”。

npm 生态。 npm 是 Node.js 自带的包管理器，全球最大的开源包仓库。你想加日志、加颜色、连数据库，大概率已经有现成的包。第 3 章会详细讲 npm。但记住一句话：包多不等于都要装。 每装一个依赖，就多一份维护、安全和体积成本。

一个生活比喻

讲稿里用餐厅点餐比喻同步和异步：

  • 同步：你点完餐，站在柜台前一直等，直到餐做好，才去做下一件事。
  • 异步：你点完餐，拿一个号码牌，去找座位玩手机。餐做好了，服务员叫你。等待的过程中，你可以干别的事。

Node.js 默认是异步的。setTimeout、fs.readFile、数据库查询，都不会卡住主线程。第 4 章会把这件事讲透。

2.4 第一个 Web 服务器

新建 server.js：

javascript
const http = require('http');

const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });
  res.end('<h1>你好，Node.js 服务器！</h1>');
});

server.listen(3000, () => {
  console.log('服务器已启动，访问 http://localhost:3000');
});

运行：

bash
node server.js

打开浏览器，访问 http://localhost:3000。看到“你好，Node.js 服务器！”了吗？

这三行代码发生了什么

http.createServer 创建一个 HTTP 服务器，参数是一个回调函数。每当有请求进来，Node.js 就调用这个函数，传入两个对象：

  • req：请求对象，包含方法、URL、请求头、请求体。
  • res：响应对象，用来设置状态码、响应头、发送响应内容。

res.writeHead(200, { 'Content-Type': ... }) 设置状态码和响应头。res.end(...) 结束响应并发送内容。

server.listen(3000) 让服务器监听 3000 端口。回调在监听成功后执行，打印提示。

中文乱码的坑

如果只写：

javascript
res.end('<h1>你好</h1>');

浏览器可能显示乱码。原因不是 Node.js 不支持中文，而是浏览器不知道这段字节用什么字符集解码。HTTP 响应头里的 Content-Type 没有指定 charset，浏览器就会用默认编码猜。

正确写法：

javascript
res.writeHead(200, { 'Content-Type': 'text/html; charset=utf-8' });

返回 JSON 时同理：

javascript
res.writeHead(200, { 'Content-Type': 'application/json; charset=utf-8' });

这是第一个坑，也是以后每次写接口都要注意的地方。只要响应体里有中文，就检查 charset=utf-8。

服务器为什么不会退出

运行 node hello.js，程序打印完就退出了。运行 node server.js，程序会一直停在那里。因为 server.listen 让 Node.js 的事件循环里有一个活跃的句柄（handle），事件循环认为“还有事情要做”，所以进程不退出。

按 Ctrl + C 发送 SIGINT，进程结束。这也是后面实现“优雅关闭”的基础：收到信号后，先停止接收新请求，再关闭数据库连接，最后退出。

2.5 CommonJS：把代码拆成模块

一个项目不可能把所有代码写在一个文件里。Node.js 采用 CommonJS 规范：每个文件就是一个模块，模块内部的变量默认私有，只有通过 module.exports 暴露出去，其他文件才能使用。

写一个工具模块

新建 utils.js：

javascript
function generateId() {
  return Math.random().toString(36).slice(2, 10);
}

function formatTime(date) {
  const y = date.getFullYear();
  const m = String(date.getMonth() + 1).padStart(2, '0');
  const d = String(date.getDate()).padStart(2, '0');
  const hh = String(date.getHours()).padStart(2, '0');
  const mm = String(date.getMinutes()).padStart(2, '0');
  const ss = String(date.getSeconds()).padStart(2, '0');
  return `${y}-${m}-${d} ${hh}:${mm}:${ss}`;
}

module.exports = {
  generateId,
  formatTime
};

在 app.js 里使用：

javascript
const { generateId, formatTime } = require('./utils');

console.log('随机ID：', generateId());
console.log('当前时间：', formatTime(new Date()));

运行：

bash
node app.js

四个必须记住的细节

第一，require('./utils') 里的 ./ 不能省略。 ./ 表示当前目录；省略了，Node.js 会去 node_modules 里找名为 utils 的包，找不到就报 MODULE_NOT_FOUND。../ 表示上一级目录，/ 开头表示绝对路径。

第二，module.exports 和 exports 的关系。 模块开始时，Node.js 隐式创建了：

javascript
const exports = module.exports;

所以 exports.foo = 1 和 module.exports.foo = 1 效果一样，都是往同一个对象上挂属性。但如果你写：

javascript
exports = { foo: 1 };

这只是让 exports 指向了一个新对象，module.exports 还是原来的空对象，外部 require 拿到的是空对象。所以推荐直接使用 module.exports，避免这个坑。

第三，模块只会执行一次。 第一次 require 时，Node.js 执行模块代码，把结果缓存起来；再次 require 同一个路径，直接返回缓存，不会重复执行。这就是为什么数据库连接池、事件总线这类“单例”适合放在模块里。

第四，模块有独立作用域。 在 utils.js 里定义的 generateId，不会自动变成全局函数。每个模块的代码都被包在一个函数里（Node.js 称之为模块包装器），所以变量不会污染全局。

把服务器拆成模块

现在把 server.js 改造成模块化结构：

response.js：

javascript
function html(body) {
  return {
    statusCode: 200,
    headers: { 'Content-Type': 'text/html; charset=utf-8' },
    body
  };
}

function json(data, statusCode = 200) {
  return {
    statusCode,
    headers: { 'Content-Type': 'application/json; charset=utf-8' },
    body: JSON.stringify(data)
  };
}

module.exports = { html, json };

server.js：

javascript
const http = require('http');
const response = require('./response');

const server = http.createServer((req, res) => {
  if (req.url === '/') {
    const result = response.html('<h1>你好，Node.js 服务器！</h1>');
    res.writeHead(result.statusCode, result.headers);
    return res.end(result.body);
  }

  const result = response.json({ error: '接口不存在' }, 404);
  res.writeHead(result.statusCode, result.headers);
  res.end(result.body);
});

server.listen(3000, () => {
  console.log('服务器已启动，访问 http://localhost:3000');
});

这样 server.js 只负责“接收请求、选择响应”，response.js 负责“构造响应”。文件小，职责清楚。项目变大后，这个习惯会救你很多次。

3.1 npm 是什么

npm 全称 Node Package Manager，是 Node.js 自带的包管理器。安装 Node.js 时，npm 已经一起装好了。第 2 章验证过 npm -v，能看到版本号就说明可用。

npm 有两个主要作用：

  1. 管理依赖。 你想用别人写好的代码，只需要 npm install 包名，它就会把包下载到 node_modules 目录，并记录到 package.json。
  2. 管理项目脚本。 你可以在 package.json 的 scripts 里定义命令，比如 npm run dev 启动开发服务器。

全世界有超过两百万个开源包。理论上，你需要的功能几乎都有人写好了。但这也带来一个问题：选择太多，质量参差不齐。 安装一个包之前，至少看三件事：最近一次更新是什么时候、周下载量多少、有没有明显的安全漏洞。一个两年没维护的包，可能在新版 Node.js 上直接跑不起来。

课堂回声：讲稿里特意强调“不要盲目安装，要选维护活跃、文档齐全的包”。这句话在你以后接手的每一个项目里都成立。

3.2 创建项目文件夹

每个项目一个独立文件夹，名字用英文，不要有中文和空格。比如：

  • 待办事项：todo-app
  • 博客：blog-api
  • 图书管理：library-api

为什么不能用中文和空格？不是 Node.js 不支持，而是很多工具链（尤其是部署、Docker、CI）对中文路径和空格的处理并不一致。轻则脚本报错，重则依赖安装失败。养成用英文短名、短横线分隔的习惯，能省掉很多莫名其妙的麻烦。

3.3 初始化 package.json

在项目根目录打开终端，运行：

bash
npm init -y

-y 表示全部使用默认值。运行后，文件夹里多了一个 package.json，内容大概是：

json
{
  "name": "todo-app",
  "version": "1.0.0",
  "description": "",
  "main": "index.js",
  "scripts": {
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "keywords": [],
  "author": "",
  "license": "ISC"
}

几个字段的含义：

  • name：项目名称。只能包含小写字母、数字、短横线、下划线，不能有中文和大写字母。发布到 npm 时它必须唯一；本地项目只要合法即可。
  • version：版本号，默认 1.0.0。遵循语义化版本 主版本.次版本.修订号。
  • main：入口文件。别人 require('你的包') 时，默认加载这个文件。
  • scripts：自定义命令。npm run 脚本名 就会执行对应的命令。
  • dependencies / devDependencies：现在还没有，安装包后会自动出现。
  • license：开源协议。教学项目用 MIT 即可。

手动完善字段

把 package.json 改成下面这样：

json
{
  "name": "todo-app",
  "version": "1.0.0",
  "private": true,
  "description": "一个用 Node.js、Express、EJS 与 MySQL 构建的待办事项应用",
  "main": "src/server.js",
  "engines": {
    "node": ">=18.17"
  },
  "scripts": {
    "start": "node src/server.js",
    "dev": "nodemon src/server.js",
    "test": "node --test"
  },
  "keywords": ["nodejs", "express", "todo", "ejs", "mysql"],
  "author": "你的名字",
  "license": "MIT"
}

private: true 防止你一不小心把项目发布到 npm。engines 声明 Node.js 版本要求，团队协作和部署时会用到。main 指向真正的入口 src/server.js，虽然这个文件现在还没创建。

3.4 安装依赖

第一个包：chalk

先装一个用于练习的包：

bash
npm install chalk@4

为什么指定 @4？因为 chalk 5 及以后只支持 ES Module，在 CommonJS 里 require('chalk') 会报错。我们目前用的是 CommonJS，所以装 4.x。这个细节在讲稿里专门提过，是很典型的“版本兼容”问题。

安装完成后：

  • 文件夹里多了 node_modules 目录，里面是 chalk 的代码和它的依赖。
  • package.json 里多了 dependencies：
json
"dependencies": {
  "chalk": "^4.1.2"
}

^4.1.2 是语义化版本范围，表示“允许安装 4.x 的最新版本，但不跨到 5.0.0”。常见的范围符号：

写法 含义 例子
^4.1.2 不改变主版本，允许次版本和修订号升级 4.1.2 → 4.9.0
~4.1.2 不改变次版本，只允许修订号升级 4.1.2 → 4.1.9
4.1.2 精确锁定 只能 4.1.2
* 任意版本 不推荐
>=4 <5 范围 4.x

开发依赖：nodemon

每次改代码都要 Ctrl + C 再重新运行，太麻烦。nodemon 会监听文件变化，自动重启服务器：

bash

--save-dev（简写 -D）表示这是开发依赖，记录在 devDependencies 里。为什么区分？

  • dependencies：项目运行时需要的包，比如 Express、EJS、mysql2。部署到生产环境也要安装。
  • devDependencies：只在开发时需要的包，比如 nodemon、测试工具、代码检查工具。生产环境可以不装。

部署时常用：

bash
npm install --omit=dev

3.5 package-lock.json 与 node_modules

安装依赖后，除了 node_modules，还会出现 package-lock.json。它记录每个包的精确版本和依赖树，保证团队每个人、每台服务器安装出来的版本一致。

三条规则：

  1. package-lock.json 要提交到 Git。 它不是你手动改的，但必须共享。
  2. node_modules 不要提交。 它体积大、平台相关，而且可以由 package.json + lock 文件重新生成。
  3. 不要手动改 lock 文件。 需要更新依赖时，用 npm install 包名@版本 或 npm update。

如果团队拉取代码后想严格按照 lock 文件安装，用：

bash
npm ci

npm ci 会先删除 node_modules，再按 lock 文件安装，速度更快、结果更可复现。CI/CD 环境里通常用 npm ci 而不是 npm install。

3.6 用 scripts 管理命令

package.json 的 scripts 是项目的“命令面板”。最终项目里至少有这些：

json
"scripts": {
  "start": "node src/server.js",
  "dev": "nodemon src/server.js",
  "test": "node --test",
  "test:watch": "node --test --watch",
  "db:init": "node scripts/init-db.js",
  "db:seed": "node scripts/seed.js"
}

运行方式：

bash
npm start
npm run dev
npm test
npm run db:init

注意：npm start 和 npm test 是 npm 的内置简写，可以省略 run；其他脚本必须写 npm run 脚本名。

scripts 的好处：

  • 新成员不用记住复杂的命令，看 package.json 就知道怎么启动。
  • 不同平台可以写不同命令，或者用 Node 脚本抹平差异。
  • CI/CD 可以直接调用 npm test，不需要关心测试框架是什么。

第 4 章 异步编程：Node.js 的心脏

本章版本：v0.3　本章产出：回调、Promise、async/await 三版异步代码；一个模拟异步数据层 本章目标：理解同步与异步的区别，掌握 Promise 和 async/await，知道什么时候会“顺序执行”、什么时候会“并发执行”。

4.1 同步与异步

先看一段同步代码：

javascript
console.log('开始');
const result = 1 + 1;
console.log('结果：', result);
console.log('结束');

输出顺序是：

text
开始
结果： 2
结束

这是同步：一行一行执行，上一行没完成，下一行不会开始。1 + 1 这种 CPU 计算非常快，同步没问题。

再看异步：

javascript
console.log('开始');

setTimeout(() => {
  console.log('两秒后执行');
}, 2000);

console.log('结束');

输出顺序是：

text
开始
结束
两秒后执行

setTimeout 没有阻塞后面的代码。它把回调函数交给定时器，时间到了，事件循环再把回调放回主线程执行。等待的两秒里，主线程可以继续处理别的事情。

餐厅比喻

  • 同步：你点完餐，站在柜台前一直等，直到餐做好，才去做下一件事。
  • 异步：你点完餐，拿一个号码牌，去找座位玩手机。餐做好了，服务员叫你。等待的过程中，你可以干别的事。

Node.js 默认就是异步的。读写文件、访问数据库、发送网络请求，这些操作不会阻塞主线程。主线程继续处理其他请求，等操作完成后再通过回调通知你。这就是 Node.js 高并发能力的来源。

单线程为什么能高并发

因为大部分 Web 请求的时间花在“等”上：等磁盘、等数据库、等网络。同步模型下，一个请求等待时，线程就被占住了；要处理更多请求，只能开更多线程，线程多了，内存和上下文切换成本都上来了。

Node.js 的主线程在等待 I/O 时不被占住，而是去处理下一个请求。等 I/O 完成，回调排队回来执行。一个主线程可以支撑大量并发连接。代价是：只要有一段 CPU 密集的代码长时间占用主线程，所有请求都会被卡住。 所以 Node.js 适合 I/O 密集型应用，不适合视频转码、大规模图像处理这类 CPU 密集型任务（除非用 worker_threads 拆分）。

4.2 回调函数

最早的异步处理方式是回调函数：

javascript
function fetchData(callback) {
  setTimeout(() => {
    const data = { id: 1, name: '张三' };
    callback(data);
  }, 1000);
}

console.log('请求数据...');
fetchData((data) => {
  console.log('收到数据：', data);
});
console.log('请求已发出，继续做别的事');

输出：

text
请求数据...
请求已发出，继续做别的事
收到数据： { id: 1, name: '张三' }

回调函数就是“等事情做完后，回来调用这个函数”。

Node.js 的错误优先回调

Node.js 的很多原生 API 采用“错误优先回调”（error-first callback）：回调的第一个参数是错误，第二个参数才是结果。

javascript
const fs = require('fs');

fs.readFile('example.txt', 'utf8', (err, data) => {
  if (err) {
    console.error('读取失败：', err.message);
    return;
  }
  console.log('文件内容：', data);
});

规则很简单：先判断 err，有错就尽早 return，不要把成功逻辑写在错误分支里。

回调地狱

如果多个异步操作依次依赖，回调会一层层嵌套：

javascript
fetchData((data) => {
  fetchMore(data.id, (more) => {
    fetchDetail(more.detailId, (detail) => {
      // 层层嵌套，难以维护
    });
  });
});

这就是“回调地狱”。问题不只是缩进深，而是：

  • 错误处理分散在每一层，容易漏。
  • 中间变量作用域层层嵌套，难以复用。
  • 想加一个“无论成功失败都执行”的逻辑，要写很多遍。

Promise 就是为了解决这些问题出现的。

4.3 Promise

Promise 是一个对象，表示“未来会完成的操作”。它有三种状态：

  • pending：进行中。
  • fulfilled：成功。
  • rejected：失败。

状态一旦从 pending 变成 fulfilled 或 rejected，就不会再变。

用 Promise 改造上面的例子：

javascript
function fetchData() {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      const success = true;
      if (success) {
        resolve({ id: 1, name: '张三' });
      } else {
        reject(new Error('请求失败'));
      }
    }, 1000);
  });
}

fetchData()
  .then((data) => {
    console.log('收到数据：', data);
  })
  .catch((err) => {
    console.error('出错：', err.message);
  })
  .finally(() => {
    console.log('请求结束');
  });

resolve 表示成功，reject 表示失败。.then 处理成功，.catch 处理失败，.finally 无论成功失败都会执行。

链式调用

Promise 的 .then 返回一个新的 Promise，所以可以链式调用：

javascript
fetchData()
  .then((data) => {
    console.log('第一步：', data);
    return fetchMore(data.id);
  })
  .then((more) => {
    console.log('第二步：', more);
    return fetchDetail(more.detailId);
  })
  .then((detail) => {
    console.log('第三步：', detail);
  })
  .catch((err) => {
    console.error('任何一步出错都会到这里：', err.message);
  });

回调地狱的嵌套变成了纵向的链。错误只需要在最后 .catch 一次，中间任何一步 reject，都会跳过后面的 .then，直接进入 .catch。

并行执行：Promise.all

如果几个异步操作互不依赖，不要一个一个等，可以同时发起：

javascript
const [todos, stats] = await Promise.all([
  todoService.getAll(),
  todoService.getStats()
]);

Promise.all 等待所有 Promise 成功，返回结果数组；只要有一个失败，整体立刻失败。

相关的还有：

  • Promise.allSettled：等待所有 Promise 结束，不管成功失败，返回每个的结果。适合“批量操作，允许部分失败”。
  • Promise.race：第一个结束的 Promise 决定结果。适合“超时控制”。
  • Promise.any：第一个成功的 Promise 决定结果。适合“多个镜像源，谁先成功用谁”。

4.4 async/await

async/await 是 ES2017 引入的语法，让异步代码看起来像同步代码。它是目前最推荐的写法。

javascript
async function main() {
  try {
    console.log('请求数据...');
    const data = await fetchData();
    console.log('收到数据：', data);

    const more = await fetchMore(data.id);
    console.log('更多数据：', more);
  } catch (err) {
    console.error('出错：', err.message);
  }
}

main();

几个要点：

  • async 函数总是返回一个 Promise。函数里 return 1，外部拿到的是 Promise.resolve(1)。
  • await 只能用在 async 函数内部（顶层 await 在 ES Module 中可用）。
  • await 会暂停当前函数的执行，等待 Promise 完成，但不会阻塞主线程。暂停的是这个函数，事件循环继续处理别的任务。
  • 用 try/catch 捕获错误，和同步代码一样。

顺序与并发

这是初学者最容易写错的地方。看两段代码：

javascript
// 顺序执行：总耗时约 2 秒
const user = await fetchUser(1);      // 1 秒
const todos = await fetchTodos(1);    // 1 秒
javascript
// 并发执行：总耗时约 1 秒
const [user, todos] = await Promise.all([
  fetchUser(1),
  fetchTodos(1)
]);

如果两个操作互不依赖，用 Promise.all 并发；如果后一个需要前一个的结果，只能顺序 await。

四个常见坑

坑一：忘记 await。

javascript
const todo = todoService.getById(1); // 得到的是 Promise，不是 todo
console.log(todo.title);             // undefined

只要函数是 async，调用它就必须 await，否则拿到的是 Promise。TypeScript 能在编译期发现这类错误，纯 JavaScript 只能靠命名约定和测试。

坑二：在循环里串行 await。

javascript
for (const id of ids) {
  const todo = await getTodo(id); // 一条一条等
}

如果这些请求互不依赖，应该用 Promise.all(ids.map((id) => getTodo(id)))。但要注意：并发太多可能压垮数据库，实际项目里要控制并发数。

坑三：async 函数里的错误没有 try/catch。

javascript
app.get('/todos', async (req, res) => {
  const todos = await data.getAll(); // 一旦抛错，Express 4 不会自动捕获
  res.json(todos);
});

Express 4 不会捕获 async 函数返回的 rejected Promise，请求会一直挂起。解决方案有两种：每个路由写 try/catch 并 next(err)，或者用第 8 章的 asyncHandler 包装器。

坑四：没有处理 unhandledRejection。

一个 Promise 被 reject，但没有任何 .catch 或 try/catch，Node.js 会触发 unhandledRejection。默认行为在 Node.js 15 之后是终止进程。开发时至少加一个监听器，把错误打出来：

javascript
process.on('unhandledRejection', (reason) => {
  console.error('未处理的 Promise 拒绝：', reason);
});

生产环境应该记录日志并告警，而不是简单忽略。

4.5 事件循环：代码到底按什么顺序跑

看一个经典面试题：

javascript
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

process.nextTick(() => console.log('4'));

console.log('5');

输出顺序是：

text
1
5
4
3
2

为什么？

  • 同步代码先执行：1、5。
  • 同步代码执行完后，先清空 process.nextTick 队列：4。
  • 再清空微任务队列（Promise 的 .then）：3。
  • 然后进入事件循环的各个阶段，定时器回调在 timers 阶段执行：2。

你不需要背下所有阶段，但需要记住三条优先级：

  1. 同步代码。
  2. 微任务（process.nextTick 优先于 Promise）。
  3. 宏任务（setTimeout、setInterval、I/O 回调）。

这解释了为什么 setTimeout(fn, 0) 不是“立刻执行”，而是“尽快在下一轮事件循环执行”。也解释了为什么 Promise 的回调总比 setTimeout 先执行。

4.6 项目实践：模拟异步数据层

现在把异步用到项目里。第 5 章才会正式写数据层，这一节先做一个“内存数组 + setTimeout”的雏形，体会“对外异步、对内同步”的接口。

新建 src/data.js：

javascript
let todos = [
  { id: 1, title: '学习 Node.js', completed: false },
  { id: 2, title: '完成项目立项', completed: true }
];

let nextId = 3;

function delay(ms = 300) {
  return new Promise((resolve) => setTimeout(resolve, ms));
}

async function getAll() {
  await delay();
  return todos.map((todo) => ({ ...todo }));
}

async function getById(id) {
  await delay();
  const todo = todos.find((item) => item.id === id);
  if (!todo) throw new Error('待办不存在');
  return { ...todo };
}

async function create(title) {
  await delay();
  const todo = { id: nextId++, title, completed: false };
  todos.push(todo);
  return { ...todo };
}

async function update(id, patch) {
  await delay();
  const todo = todos.find((item) => item.id === id);
  if (!todo) throw new Error('待办不存在');
  Object.assign(todo, patch);
  return { ...todo };
}

async function remove(id) {
  await delay();
  const index = todos.findIndex((item) => item.id === id);
  if (index === -1) throw new Error('待办不存在');
  const [deleted] = todos.splice(index, 1);
  return { ...deleted };
}

module.exports = { getAll, getById, create, update, remove };

delay 用 setTimeout 模拟数据库/文件的 300 毫秒延迟。为什么要模拟延迟？因为真实的 I/O 本来就是异步的。如果现在就写成同步数组操作，等你换成文件或数据库时，调用方所有的代码都要加 await，接口就变了。从第一天起就用异步接口，后面换实现时调用方不用改。

新建 test-data.js：

javascript
const data = require('./src/data');

async function main() {
  try {
    console.log('全部数据：', await data.getAll());
    console.log('单个数据：', await data.getById(1));

    const created = await data.create('新的待办');
    console.log('创建成功：', created);

    const updated = await data.update(created.id, { completed: true });
    console.log('更新成功：', updated);

    const deleted = await data.remove(created.id);
    console.log('删除成功：', deleted);

    console.log('最终全部：', await data.getAll());
  } catch (err) {
    console.error('操作失败：', err.message);
  }
}

main();

运行：

bash
node test-data.js

观察输出顺序。每个操作之间都隔了约 300 毫秒，因为我们在 await。如果去掉 await，会看到所有操作几乎同时开始，顺序就乱了——这也是“忘记 await”的直观后果。

5.1 为什么不能把数据操作写在路由里

第 4 章的 data.js 已经能增删改查了，但它把所有事情混在一起：存数据、生成 id、校验参数、抛错误。现在只有五六个函数，看起来还好；等加了页面、API、数据库，问题会一个接一个冒出来。

假设我们在路由里直接操作数组：

javascript
app.post('/api/todos', (req, res) => {
  if (!req.body.title) {
    return res.status(400).json({ error: '标题不能为空' });
  }
  todos.push({ id: nextId++, title: req.body.title, completed: false });
  res.status(201).json(todos[todos.length - 1]);
});

这段代码能跑，但有几个隐患：

  1. 校验规则分散。 API 路由写一遍“标题不能为空”，页面路由再写一遍，将来加一个导入功能还要写第三遍。规则一改，三处都要改。
  2. 无法替换存储。 数据直接存在数组里，换成 JSON 文件或 MySQL 时，所有路由都要重写。
  3. 错误处理不统一。 路由里到处是 if (!title) return res.status(400)...，真正的异常（文件损坏、数据库断开）反而没人管。
  4. 无法测试。 要测业务逻辑，必须先启动 HTTP 服务器、构造请求、解析响应。

解决办法是分层：路由只负责 HTTP，业务层负责规则，仓库层负责存取。

5.2 三个概念：仓库、业务层、依赖注入

仓库（Repository）

仓库只做一件事：把数据存进去、取出来。 它不关心 HTTP，不关心“标题不能为空”，甚至不关心 completed 应该怎么展示。它只提供一组方法：

text
getAll(filters)  -> Todo[]
getById(id)      -> Todo | null
create({title})   -> Todo
update(id, patch) -> Todo | null
remove(id)        -> Todo | null
getStats()        -> { total, active, completed }
close()           -> void

注意 getById 找不到时返回 null，而不是抛错。为什么？因为“找不到”对仓库来说是一个正常的查询结果，不是异常。要不要把 null 变成 404，是业务层的决定。

业务层（Service）

业务层负责规则：

  • 标题不能为空，长度不超过 255，去除首尾空格。
  • id 必须是正整数。
  • completed 必须是布尔值。
  • 找不到待办时，抛出 NotFoundError。
  • 数据变更后，发出事件（第 6 章接入）。

它调用仓库，但不知道仓库背后是数组、JSON 文件还是 MySQL。

依赖注入（Dependency Injection）

业务层不自己 new 一个仓库，而是由外部把仓库“注入”进来：

javascript
const service = createTodoService(repository, bus);

这样做的好处：

  • 测试时传入内存仓库，不需要真实数据库。
  • 生产时传入 JSON 或 MySQL 仓库，业务代码不变。
  • 一个业务层可以同时被 API 路由和页面路由使用。

这不是什么高深的设计模式，只是“不要在函数内部写死依赖”这个朴素原则。

5.3 定义错误类型

先创建 src/errors.js：

javascript
class AppError extends Error {
  constructor(message, status = 500, code = 'INTERNAL_ERROR') {
    super(message);
    this.name = 'AppError';
    this.status = status;
    this.code = code;
    this.expose = status < 500;
  }
}

class ValidationError extends AppError {
  constructor(message = '请求参数不合法') {
    super(message, 400, 'VALIDATION_ERROR');
    this.name = 'ValidationError';
  }
}

class NotFoundError extends AppError {
  constructor(message = '资源不存在') {
    super(message, 404, 'NOT_FOUND');
    this.name = 'NotFoundError';
  }
}

module.exports = { AppError, ValidationError, NotFoundError };

为什么要自定义错误，而不是直接 throw new Error('待办不存在')？

  • 状态码稳定。 错误中间件可以直接读 err.status，不需要用字符串匹配 err.message === '待办不存在'。字符串一改，匹配就失效。
  • 错误码稳定。 err.code 给前端和日志用，不会因为文案调整而变化。
  • 区分“可暴露”和“不可暴露”。 expose 为 true 的错误，消息可以返回给用户；500 错误只返回“服务器内部错误”，详细堆栈写日志。
  • 便于分类。 ValidationError、NotFoundError 可以用 instanceof 判断，也可以继续扩展 ConflictError、UnauthorizedError。

status < 500 才暴露，是一条重要的安全规则。数据库连接字符串、SQL 语句、文件绝对路径这些信息，不应该出现在用户的浏览器里。

5.4 内存仓库

第 5 章先用内存仓库，把接口跑通。创建 src/repositories/memoryTodoRepository.js：

javascript
function createMemoryTodoRepository(seed = []) {
  let todos = seed.map((todo) => ({ ...todo }));
  let nextId = todos.length > 0 ? Math.max(...todos.map((t) => t.id)) + 1 : 1;

  function clone(todo) {
    return todo ? { ...todo } : todo;
  }

  async function getAll({ status = 'all', q = '' } = {}) {
    let result = todos;
    if (status === 'active') result = result.filter((t) => !t.completed);
    if (status === 'completed') result = result.filter((t) => t.completed);
    if (q) {
      const keyword = q.toLowerCase();
      result = result.filter((t) => t.title.toLowerCase().includes(keyword));
    }
    return result
      .slice()
      .sort((a, b) => new Date(b.createdAt) - new Date(a.createdAt))
      .map(clone);
  }

  async function getById(id) {
    return clone(todos.find((t) => t.id === id)) || null;
  }

  async function create({ title }) {
    const now = new Date().toISOString();
    const todo = {
      id: nextId++,
      title,
      completed: false,
      createdAt: now,
      updatedAt: now
    };
    todos.push(todo);
    return clone(todo);
  }

  async function update(id, patch) {
    const todo = todos.find((t) => t.id === id);
    if (!todo) return null;
    if (patch.title !== undefined) todo.title = patch.title;
    if (patch.completed !== undefined) todo.completed = patch.completed;
    todo.updatedAt = new Date().toISOString();
    return clone(todo);
  }

  async function remove(id) {
    const index = todos.findIndex((t) => t.id === id);
    if (index === -1) return null;
    const [deleted] = todos.splice(index, 1);
    return clone(deleted);
  }

  async function getStats() {
    const completed = todos.filter((t) => t.completed).length;
    return { total: todos.length, active: todos.length - completed, completed };
  }

  async function close() {}

  return { getAll, getById, create, update, remove, getStats, close };
}

module.exports = { createMemoryTodoRepository };

有几个细节值得注意。

为什么返回 clone？ 如果直接把数组里的对象引用返回，调用方修改返回值，会意外改掉仓库里的数据。比如：

javascript
const todo = await repo.getById(1);
todo.title = '被改了';

如果返回的是引用，仓库里的数据也被改了，而且没有经过 update，没有更新时间，没有触发事件。返回浅拷贝可以避免这种“绕过仓库的修改”。对于只有基本类型字段的 Todo，浅拷贝就够了；如果有嵌套对象，需要深拷贝。

为什么 getAll 要排序？ 列表默认按创建时间倒序，新的在前。如果两条记录创建时间相同，用 id 倒序兜底，保证顺序稳定。排序是仓库的职责，因为不同存储的排序方式不同（JSON 用数组 sort，MySQL 用 ORDER BY）。

为什么 async 函数里没有任何 await？ 因为内存操作是同步的，但接口必须是异步的。这样将来换成文件或数据库时，调用方的 await 不需要改。接口的异步性是契约的一部分，不是实现细节。

5.5 业务数据层

创建 src/data.js。先看校验函数：

javascript
const { ValidationError, NotFoundError } = require('./errors');

const ALLOWED_STATUS = new Set(['all', 'active', 'completed']);
const MAX_TITLE_LENGTH = 255;

function normalizeTitle(value) {
  if (typeof value !== 'string') {
    throw new ValidationError('标题必须是字符串');
  }
  const title = value.trim();
  if (!title) throw new ValidationError('标题不能为空');
  if (title.length > MAX_TITLE_LENGTH) {
    throw new ValidationError(`标题不能超过 ${MAX_TITLE_LENGTH} 个字符`);
  }
  return title;
}

function normalizeId(value) {
  const id = typeof value === 'string' ? Number(value) : value;
  if (!Number.isInteger(id) || id <= 0) {
    throw new ValidationError('无效的ID格式');
  }
  return id;
}

normalizeId 接受字符串，是因为 URL 参数 req.params.id 永远是字符串。Number('abc') 是 NaN，Number('1.5') 是 1.5，都不满足 Number.isInteger，所以会被拒绝。Number('') 是 0，也会被 id <= 0 拒绝。

注意：parseInt('12abc') 会得到 12，把非法输入“宽容”地变成合法 id。用 Number + Number.isInteger 更严格，能避免这类问题。

然后是业务函数：

javascript
function createTodoService(repository, bus) {
  async function getAll(filters) {
    const status = filters?.status || 'all';
    if (!ALLOWED_STATUS.has(status)) {
      throw new ValidationError('status 只能是 all、active 或 completed');
    }
    const q = typeof filters?.q === 'string' ? filters.q.trim() : '';
    if (q.length > 100) {
      throw new ValidationError('搜索关键词不能超过 100 个字符');
    }
    return repository.getAll({ status, q });
  }

  async function getById(rawId) {
    const id = normalizeId(rawId);
    const todo = await repository.getById(id);
    if (!todo) throw new NotFoundError('待办不存在');
    return todo;
  }

  async function create(input) {
    const title = normalizeTitle(
      typeof input === 'string' ? input : input && input.title
    );
    const todo = await repository.create({ title });
    bus.emit('data:created', { type: 'todo', item: todo });
    return todo;
  }

  async function update(rawId, patch = {}) {
    const id = normalizeId(rawId);
    await getById(id);

    const safePatch = {};
    if (patch.title !== undefined) safePatch.title = normalizeTitle(patch.title);
    if (patch.completed !== undefined) {
      if (typeof patch.completed !== 'boolean') {
        throw new ValidationError('completed 必须是布尔值');
      }
      safePatch.completed = patch.completed;
    }

    if (Object.keys(safePatch).length === 0) {
      throw new ValidationError('没有可更新的字段');
    }

    const updated = await repository.update(id, safePatch);
    bus.emit('data:updated', { type: 'todo', item: updated });
    return updated;
  }

  async function toggle(rawId) {
    const todo = await getById(rawId);
    return update(todo.id, { completed: !todo.completed });
  }

  async function remove(rawId) {
    const todo = await getById(rawId);
    const deleted = await repository.remove(todo.id);
    bus.emit('data:deleted', { type: 'todo', item: deleted });
    return deleted;
  }

  async function getStats() {
    return repository.getStats();
  }

  return { getAll, getById, create, update, toggle, remove, getStats };
}

这段代码有几个设计点。

create 同时接受字符串和对象。 课堂上的 create(title) 传的是字符串，最终 API 传的是 { title }。为了兼容两种调用方式，这里做了判断。真实项目中最好只保留一种签名，避免调用方猜；书里保留兼容，是为了让你看到“接口演进”时如何不破坏旧调用。

update 只挑白名单字段。 如果用户传了 { id: 999, createdAt: '...' }，这些字段会被忽略，不会覆盖数据库里的值。这叫“mass assignment 防护”，是安全实践的一部分。

toggle 复用了 update。 先查出当前状态，再取反。这里有一个并发问题：两个请求同时 toggle，可能都读到 false，都写成 true，结果只切换了一次。单用户教学项目可以接受；如果要做严格，需要在数据库层用原子更新（UPDATE ... SET completed = NOT completed）或加锁。第 10 章会提到这个扩展点。

事件在业务层发出。 仓库只管存，业务层知道“一次创建完成了”，所以由它发 data:created。这样换成任何仓库，事件都不会丢。

5.7 这一层为什么值得

你可能会觉得：为了五个函数，写三个文件，是不是过度设计？

在只有五个函数的时候，确实有点。但项目会长大。第 6 章要换成 JSON 文件，第 10 章要换成 MySQL，第 11 章要加更多校验，第 12 章要写测试。如果没有这一层，每次变化都会波及路由和页面；有了这一层，变化被关在仓库实现里，业务接口不动，调用方不动。

这就是软件设计里最重要的一句话之一：把容易变的部分和不容易变的部分分开。

  • 容易变：数据存在哪里、SQL 怎么写、文件怎么读。
  • 不容易变：一条待办必须有标题、id 必须是正整数、找不到要返回 404。

仓库模式把“容易变”的部分隔离了，业务层守住“不容易变”的规则。

6.1 内存数据的问题

第 5 章的数据层已经很好用了，但有一个致命问题：数据存在内存里，程序一关就没了。

你可以做个实验：运行 test-data.js 创建一条待办，然后关掉终端，再运行一次。新进程里，内存数组重新初始化，刚才的数据不见了。

这就是“持久化”要解决的问题。持久化有很多种方式：写文件、写数据库、写对象存储。本章先做最简单的一种：把整个数组写进一个 JSON 文件。

它不适合大数据量，也不适合多进程并发，但它足够简单，能让你在没有数据库的情况下，先把“数据能存下来”这件事跑通。第 10 章会把它换成 MySQL。

6.2 fs 模块：同步与异步

fs 是 Node.js 的核心模块，全称 File System。它提供读写文件、操作目录、查看文件状态等能力。Node.js 能做后端、能持久化数据，fs 是最基础的一环。

fs 的 API 分两类：

  • 同步方法：readFileSync、writeFileSync、mkdirSync。会阻塞事件循环，只适合脚本启动阶段，比如读取配置。
  • 异步方法：readFile、writeFile、mkdir。不会阻塞，服务端开发优先使用。

异步方法又分两种风格：回调和 Promise。回调风格是 Node.js 的传统写法：

javascript
const fs = require('fs');

fs.readFile('data/todos.json', 'utf8', (err, raw) => {
  if (err) {
    console.error('读取失败：', err.message);
    return;
  }
  const todos = JSON.parse(raw);
  console.log('待办数量：', todos.length);
});

Promise 风格来自 fs/promises：

javascript
const fs = require('fs/promises');

async function readTodos() {
  try {
    const raw = await fs.readFile('data/todos.json', 'utf8');
    return JSON.parse(raw);
  } catch (err) {
    console.error('读取失败：', err.message);
    return [];
  }
}

本书统一使用 fs/promises，因为它和 async/await 配合最好：不需要传回调，不需要手动判断 err，用 try/catch 统一处理。

6.3 路径：不要用相对路径

先看一个坑：

javascript
const fs = require('fs/promises');

await fs.readFile('data/todos.json', 'utf8');

这段代码能不能跑，取决于你从哪个目录启动 Node.js：

  • 在项目根目录运行 node src/test.js，当前工作目录是项目根，data/todos.json 能找到。
  • 在 src 目录里运行 node test.js，当前工作目录是 src，它会去找 src/data/todos.json，找不到。

相对路径是相对于进程的当前工作目录（process.cwd()），不是相对于当前文件。 这非常容易出错。

正确做法是用 path 模块，基于 __dirname（当前文件所在目录）拼绝对路径：

javascript
const path = require('path');

const DATA_FILE = path.join(__dirname, '..', 'data', 'todos.json');

假设文件是 src/repositories/jsonTodoRepository.js：

  • __dirname 是 .../src/repositories。
  • .. 回到 src。
  • 再 .. 回到项目根。
  • 拼上 data/todos.json，得到项目根下的绝对路径。

无论从哪个目录启动，结果都一样。

在 ES Module 中没有 __dirname，需要用 import.meta.url + fileURLToPath 换算。第 12 章会讲 ESM 迁移。

6.4 读取 JSON：处理 ENOENT

一个健壮的读取函数，要处理三种情况：

  1. 文件存在且是合法 JSON：解析并返回数组。
  2. 文件不存在：返回空数组，让程序能正常启动。
  3. 文件存在但不是合法 JSON：抛出明确的错误，不要静默吞掉。
javascript
const fs = require('fs/promises');
const { AppError } = require('../errors');

async function readFile() {
  try {
    const raw = await fs.readFile(filePath, 'utf8');
    const parsed = JSON.parse(raw);
    if (!Array.isArray(parsed)) {
      throw new AppError('数据文件格式错误：根节点必须是数组', 500, 'DATA_FILE_INVALID');
    }
    return parsed;
  } catch (err) {
    if (err.code === 'ENOENT') return [];
    if (err instanceof AppError) throw err;
    if (err instanceof SyntaxError) {
      throw new AppError(`数据文件不是合法 JSON：${filePath}`, 500, 'DATA_FILE_INVALID');
    }
    throw err;
  }
}

ENOENT 是 “Error NO ENTry” 的缩写，表示文件或目录不存在。第一次运行时文件还没创建，返回空数组，程序就能正常启动。

注意 JSON.parse 抛的是 SyntaxError。如果直接把它抛给上层，错误信息会是一串位置描述，用户看不懂。我们把它包装成 AppError，带上明确的中文提示和错误码。

不要这样做：

javascript
try {
  return JSON.parse(await fs.readFile(filePath, 'utf8'));
} catch {
  return [];
}

这会把“文件损坏”也当成“文件不存在”，悄悄返回空数组。用户以为数据丢了，实际上是被代码吞了。错误要分类处理，不能一把 catch 全吃掉。

6.5 写入 JSON：临时文件 + rename

最直接的写法：

javascript
await fs.writeFile(filePath, JSON.stringify(todos, null, 2), 'utf8');

但这里有一个风险：如果写入过程中进程崩溃、磁盘满、或者另一个请求同时读文件，可能读到一个“写了一半”的 JSON，JSON.parse 直接失败。

更稳妥的做法是原子写入：

  1. 把内容写到同目录下的临时文件。
  2. 写完后，用 rename 把临时文件替换成目标文件。
javascript
async function writeFile(todos) {
  await fs.mkdir(path.dirname(filePath), { recursive: true });
  const tempFile = `${filePath}.${process.pid}.${Date.now()}.tmp`;
  await fs.writeFile(tempFile, JSON.stringify(todos, null, 2), 'utf8');
  await fs.rename(tempFile, filePath);
}

rename 在同一文件系统内是原子操作：要么旧文件还在，要么新文件完整出现，不会出现“半个文件”。fs.mkdir(..., { recursive: true }) 确保父目录存在；即使 data/ 被删了，程序也能自动恢复。

严格来说，Windows 上的 rename 覆盖行为、断电时的磁盘缓存，都会影响“绝对原子”。但对教学项目来说，这个模式已经比直接 writeFile 可靠得多。生产环境应该用数据库的事务，或者专门的写入方案。

6.6 并发写：一个 Promise 队列

假设两个请求同时创建待办：

text
请求 A：读取 [1,2] → 追加 3 → 写入 [1,2,3]
请求 B：读取 [1,2] → 追加 3 → 写入 [1,2,3]

两个请求都读到旧数据，都写入了自己的结果，最后只有一条新数据，另一条被覆盖。这就是“读-改-写”竞态。

解决办法不是加锁（Node.js 没有内置的互斥锁），而是把写操作串行化：

javascript
let writeQueue = Promise.resolve();

function withWriteLock(operation) {
  const result = writeQueue.then(operation, operation);
  writeQueue = result.then(
    () => undefined,
    () => undefined
  );
  return result;
}

writeQueue 保存“最后一个写操作的完成状态”。新的写操作排在它后面，不管前一个成功还是失败，都会继续执行。result.then(..., ...) 里两个回调都返回 undefined，是为了让队列不会因为某次失败而断掉。

创建操作：

javascript
async function create({ title }) {
  return withWriteLock(async () => {
    const todos = await readFile();          // 在锁内读
    const nextId = todos.length > 0
      ? Math.max(...todos.map((t) => t.id)) + 1
      : 1;
    const now = new Date().toISOString();
    const todo = { id: nextId, title, completed: false, createdAt: now, updatedAt: now };
    todos.push(todo);
    await writeFile(todos);
    return { ...todo };
  });
}

读和写都要在锁内。 如果只在写的时候加锁，两个请求仍然可能读到同一份旧数据。

更新和删除同理：

javascript
async function update(id, patch) {
  return withWriteLock(async () => {
    const todos = await readFile();
    const todo = todos.find((item) => item.id === id);
    if (!todo) throw new NotFoundError('待办不存在');
    if (patch.title !== undefined) todo.title = patch.title;
    if (patch.completed !== undefined) todo.completed = patch.completed;
    todo.updatedAt = new Date().toISOString();
    await writeFile(todos);
    return { ...todo };
  });
}

getAll 和 getById 是读操作，不需要进写队列，但为了不读到“正在写”的中间状态，可以先 await writeQueue，等当前写操作完成再读：

javascript
async function getAll(filters) {
  await writeQueue;
  const todos = await readFile();
  // 过滤、排序、返回副本
}

这个队列只在单个 Node.js 进程内有效。如果你用 PM2 启动了多个实例，或者两台机器共享同一个 JSON 文件，队列救不了你。那种场景必须用数据库，或者文件锁。知道一个方案的边界，比会用这个方案更重要。

6.7 事件驱动：EventEmitter

数据存下来了，接下来解决另一个问题：数据变了，怎么通知其他模块？

最直接的做法是在 create 里写日志：

javascript
async function create(title) {
  // ...
  console.log(`[日志] 新增待办：${title}`);
  return todo;
}

但很快会有第二个需求：更新缓存、发通知、写审计日志。每加一个需求，就要改一次 create。数据层越来越臃肿，而且它不应该知道“日志”“缓存”“通知”这些事。

EventEmitter 提供了一种解耦方式：数据层只负责“广播发生了什么”，谁关心谁自己监听。

基本用法

javascript
const EventEmitter = require('events');

const emitter = new EventEmitter();

emitter.on('order', (item) => {
  console.log(`收到订单：${item}`);
});

emitter.emit('order', 'Node.js 实战课程');
emitter.emit('order', 'JavaScript 高级程序设计');
  • on(eventName, listener)：注册监听器，每次事件触发都执行。
  • once(eventName, listener)：只执行一次，执行后自动移除。
  • off / removeListener：移除指定监听器。
  • removeAllListeners：移除某个事件的所有监听器。
  • emit(eventName, ...args)：触发事件，后面的参数传给监听器。

once 适合“首次登录欢迎”“初始化完成通知”这类只关心一次的场景：

javascript
emitter.once('userLogin', (username) => {
  console.log(`[欢迎] 首次登录：${username}`);
});

error 事件是特殊的

如果 emit('error', err) 时没有任何监听器，Node.js 会把错误抛出来，甚至终止进程。所以如果你要发 error 事件，必须确保有监听器：

javascript
bus.on('error', (err) => {
  console.error('事件总线错误：', err);
});

本书的数据总线不使用 error 事件，错误通过 throw 和错误中间件处理，避免这套特殊规则带来的混淆。

项目中的事件总线

创建 src/eventBus.js：

javascript
const EventEmitter = require('events');

class DataEventBus extends EventEmitter {}

const bus = new DataEventBus();

module.exports = bus;

为什么用 class DataEventBus extends EventEmitter {} 而不是直接 new EventEmitter()？一是给类型一个明确的名字，调试时堆栈里能看到；二是将来可以在这个类上加重试、日志、监听器数量限制等能力，而不影响调用方。

在业务层发事件：

javascript
const bus = require('./eventBus');

async function create(input) {
  // ... 校验、调用仓库
  const todo = await repository.create({ title });
  bus.emit('data:created', { type: 'todo', item: todo });
  return todo;
}

async function update(id, patch) {
  // ... 更新
  const updated = await repository.update(id, safePatch);
  bus.emit('data:updated', { type: 'todo', item: updated });
  return updated;
}

async function remove(id) {
  // ... 删除
  const deleted = await repository.remove(id);
  bus.emit('data:deleted', { type: 'todo', item: deleted });
  return deleted;
}

事件名用 data:created 这种“资源:动作”的格式，比 created 更清晰，将来加 user:created 也不会冲突。payload 用对象，包含 type 和 item，方便监听器判断资源类型。

监听事件

在 server.js 或单独的监听器模块里：

javascript
bus.on('data:created', ({ item }) => {
  console.log(`[data:created] #${item.id} ${item.title}`);
});

bus.on('data:updated', ({ item }) => {
  console.log(`[data:updated] #${item.id} completed=${item.completed}`);
});

bus.on('data:deleted', ({ item }) => {
  console.log(`[data:deleted] #${item.id} ${item.title}`);
});

现在，数据层只负责发事件；日志模块、缓存模块、通知模块各自监听。将来要加“创建待办后发邮件提醒”，只需要新增一个监听器，不需要改 data.js。

注意：EventEmitter 的监听器是同步执行的。如果监听器里有耗时操作，会阻塞当前请求。生产环境里，重活应该丢到队列里异步处理，而不是直接在监听器里 await 一个慢操作。

第 7 章 原生 HTTP：不借助框架，把数据变成接口

本章版本：v0.6　本章产出：examples/native-server.js，一套可用的原生 HTTP REST API 本章目标：理解 HTTP 请求与响应，掌握 http.createServer、URL 解析、请求体读取、路由分发和统一 JSON 响应。

7.1 为什么还要学原生 http

你可能已经听说过 Express：一行 app.get() 就能定义一个路由，不用手动解析 URL、读取请求体。既然有框架，为什么还要用原生 http 模块？

因为只有亲手写过，才知道框架帮你做了什么。

用原生模块，你需要自己处理：

  • 请求方法判断（GET / POST / PUT / DELETE）。
  • URL 路径和查询参数解析。
  • 请求体的流式读取、大小限制、JSON 解析。
  • 响应头、状态码、JSON 序列化。
  • 路由匹配、404、错误处理。

这些东西 Express 都封装了。如果你没写过原生版本，用 Express 时就会把它当成“魔法”：不知道为什么中间件顺序重要，不知道 req.body 为什么有时是 undefined，不知道错误为什么没有返回 JSON。

先用原生写一遍，再用 Express 重写，你会清楚地看到：Express 不是另一套 HTTP，它只是把重复劳动包装成了中间件和路由。

7.2 HTTP 请求长什么样

HTTP 是浏览器和服务器之间的通信协议。一次请求包含：

  • 请求方法：GET、POST、PUT、PATCH、DELETE 等。
  • 请求路径：比如 /api/todos、/api/todos/1。
  • 请求头：Content-Type、Authorization、User-Agent 等。
  • 请求体：POST / PUT 通常带数据，GET 一般没有。

服务器返回响应：

  • 状态码：200、201、400、404、500。
  • 响应头：Content-Type、Location、Cache-Control 等。
  • 响应体：HTML、JSON、图片等。

一个最小的请求：

http
GET /api/todos?status=active HTTP/1.1
Host: localhost:3000
Accept: application/json

一个最小的响应：

http
HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

[{"id":1,"title":"学习 HTTP","completed":false}]

HTTP 是无状态的：服务器不会自动记住上一次请求是谁发的。这也是为什么登录需要 Cookie / Token，而不是“服务器记得你”。

javascript

属性 含义

req.headers 请求头对象，键名是小写

req.url 是路径加查询字符串。用 new URL() 解析：

javascript

7.5 路由分发

路由的本质是：根据方法和路径，选择处理函数。

先写两个辅助函数：

javascript
function sendJson(res, statusCode, payload, headers = {}) {
  res.writeHead(statusCode, {
    'Content-Type': 'application/json; charset=utf-8',
    ...headers
  });
  res.end(JSON.stringify(payload));
}

function sendError(res, statusCode, message, code) {
  sendJson(res, statusCode, { error: message, ...(code ? { code } : {}) });
}

主处理函数：

javascript
const server = http.createServer(async (req, res) => {
  const { pathname } = new URL(req.url, 'http://localhost');
  const method = req.method;

  try {
    if (pathname === '/api/health' && method === 'GET') {
      return sendJson(res, 200, { status: 'ok', timestamp: new Date().toISOString() });
    }

    if (pathname === '/api/todos' && method === 'GET') {
      const status = searchParams.get('status') || 'all';
      const q = searchParams.get('q') || '';
      const todos = await todoService.getAll({ status, q });
      return sendJson(res, 200, todos);
    }

    if (pathname === '/api/todos' && method === 'POST') {
      const body = await readJsonBody(req);
      const todo = await todoService.create(body);
      return sendJson(res, 201, todo, { Location: `/api/todos/${todo.id}` });
    }

    const match = pathname.match(/^\/api\/todos\/(\d+)$/);
    if (match) {
      const id = Number(match[1]);

      if (method === 'GET') {
        return sendJson(res, 200, await todoService.getById(id));
      }
      if (method === 'PUT') {
        const body = await readJsonBody(req);
        return sendJson(res, 200, await todoService.update(id, body));
      }
      if (method === 'DELETE') {
        return sendJson(res, 200, await todoService.remove(id));
      }
      if (method === 'PATCH' && pathname.endsWith('/toggle')) {
        // 这个分支不会命中，因为正则只匹配 /:id
      }
    }

    if (pathname.match(/^\/api\/todos\/(\d+)\/toggle$/) && method === 'PATCH') {
      const id = Number(pathname.split('/')[3]);
      return sendJson(res, 200, await todoService.toggle(id));
    }

    return sendError(res, 404, '接口不存在', 'NOT_FOUND');
  } catch (err) {
    if (err instanceof AppError) {
      return sendError(res, err.status, err.expose ? err.message : '服务器内部错误', err.code);
    }
    console.error('服务器错误：', err);
    return sendError(res, 500, '服务器内部错误', 'INTERNAL_ERROR');
  }
});

这段路由有两个问题需要修：

  1. searchParams 没有定义，应该从 parsedUrl 取。
  2. /api/todos/:id/toggle 应该放在 /:id 正则之前匹配，否则永远进不去。

  res.writeHead(statusCode, {
    'Content-Type': 'application/json; charset=utf-8',
    ...headers
  });
  res.end(JSON.stringify(payload));

function sendError(res, statusCode, message, code) {
  sendJson(res, statusCode, { error: message, ...(code ? { code } : {}) });

function readJsonBody(req, limit = 1024 * 100) {
  return new Promise((resolve, reject) => {
    let size = 0;
    const chunks = [];

    req.on('data', (chunk) => {
      size += chunk.length;
      if (size > limit) {
        reject(new AppError('请求体太大', 413, 'PAYLOAD_TOO_LARGE'));
        req.destroy();
        return;
      }
      chunks.push(chunk);
    });

    req.on('end', () => {
      if (chunks.length === 0) return resolve({});
      try {
        resolve(JSON.parse(Buffer.concat(chunks).toString('utf8')));
      } catch {
        reject(new AppError('JSON 格式错误', 400, 'INVALID_JSON'));
      }
    });

    req.on('error', reject);
  });
}

      }
      if (method === 'DELETE') {
        return sendJson(res, 200, await todoService.remove(id));
      }
    }

    return sendError(res, 404, '接口不存在', 'NOT_FOUND');
  } catch (err) {
    if (err instanceof AppError) {
      return sendError(
        res,
        err.status,
        err.expose ? err.message : '服务器内部错误',
        err.code
      );
    }
    console.error('服务器错误：', err);
    return sendError(res, 500, '服务器内部错误', 'INTERNAL_ERROR');
  }
});

server.listen(PORT, () => {
  console.log(`原生 HTTP 服务器已启动：http://localhost:${PORT}`);
});

7.7 原生服务器的局限

这套代码能工作，但你已经能感觉到重复：

  • 每个路由都要判断 method 和 pathname。
  • 每个处理函数都要 try/catch。
  • 每次返回 JSON 都要调用 sendJson。
  • 请求体解析、查询参数、404 处理都散在回调里。
  • 加一个中间件（日志、鉴权）要手动在每个分支里插。

第 8 章用 Express 重写时，你会看到这些重复如何被消除：

  • res.json() 替代 sendJson。
  • next(err) + 错误中间件替代每个函数的 try/catch。
  • express.Router() 把路由拆成模块。

但请记住：Express 没有让 HTTP 消失，它只是把 HTTP 的细节隐藏起来。 当你在 Express 里遇到 req.body 为 undefined、错误没有返回 JSON、静态文件 404 时，回头看看这一章，你会知道该查哪里。

8.2 路由：方法 + 路径 + 处理函数

Express 的路由语法：

javascript
app.METHOD(PATH, HANDLER)

METHOD 是小写的 HTTP 方法：get、post、put、patch、delete。PATH 是路径，HANDLER 是 (req, res, next) => {} 函数。

javascript
app.get('/api/hello', (req, res) => {
  res.json({ message: '你好，Express!' });
});

app.post('/api/echo', (req, res) => {
  res.json({ received: req.body, receivedAt: new Date().toISOString() });
});

app.put('/api/items/:id', (req, res) => {
  res.json({ message: `更新 ${req.params.id}`, body: req.body });
});

app.delete('/api/items/:id', (req, res) => {
  res.json({ message: `删除 ${req.params.id}` });
});

req.params 与 req.query

  • req.params：路径参数。/api/todos/:id 匹配 /api/todos/5，req.params.id 是字符串 '5'。
  • req.query：查询参数。/api/todos?status=active，req.query.status 是 'active'。
javascript
app.get('/api/todos/:id', (req, res) => {
  const id = Number(req.params.id);
  res.json({ id });
});

app.get('/api/search', (req, res) => {
  const { keyword = '', limit = 10 } = req.query;
  res.json({ keyword, limit });
});

两者都是字符串。limit 拿到的是 '10'，不是数字。需要数字就自己转，并校验。

路由顺序

Express 按注册顺序匹配路由。/api/todos/:id 会匹配 /api/todos/5，也会匹配 /api/todos/abc（id 是 'abc'）。如果你有更具体的路由，比如 /api/todos/stats，要放在 /:id 前面，否则 stats 会被当成 id。

javascript
app.get('/api/todos/stats', handler);  // 先注册
app.get('/api/todos/:id', handler);    // 后注册

本书的 API 没有 /stats 路由，统计放在页面里；但你要知道这个规则。

8.3 路由模块化：express.Router

一个项目的路由很多，不可能都写在 app.js 里。Express 提供 express.Router() 来拆分：

src/routes/todosApi.js：

javascript
const express = require('express');
const router = express.Router();

router.get('/', async (req, res, next) => {
  try {
    const todos = await todoService.getAll(req.query);
    res.json(todos);
  } catch (err) {
    next(err);
  }
});

router.post('/', async (req, res, next) => {
  try {
    const todo = await todoService.create(req.body);
    res.status(201).location(`/api/todos/${todo.id}`).json(todo);
  } catch (err) {
    next(err);
  }
});

module.exports = router;

在 app.js 里挂载：

javascript
const todosRouter = require('./routes/todosApi');
app.use('/api/todos', todosRouter);

todosApi.js 里的 / 实际上就是 /api/todos，/:id 就是 /api/todos/:id。挂载前缀让路由文件不需要关心自己的完整路径，复用性更好。

8.4 中间件：请求的流水线

中间件是 Express 最核心的概念。你可以把它想象成一条流水线：请求从进入服务器到返回响应，中间会经过多个“处理站”，每个处理站就是一个中间件。

中间件的签名：

javascript
(req, res, next) => {}
  • req：请求对象。
  • res：响应对象。
  • next：函数，调用它表示“交给下一个中间件”。

如果中间件既不调用 next()，也不发送响应，请求就会卡住，浏览器一直转圈，直到超时。

全局中间件

javascript
app.use((req, res, next) => {
  console.log(`[${new Date().toISOString()}] ${req.method} ${req.url}`);
  next();
});

app.use() 注册的中间件对所有请求生效。上面这个就是日志中间件。实际项目里我们直接用 morgan：

javascript
const morgan = require('morgan');
app.use(morgan('dev'));

终端会打印：

text
GET /todos 200 12.345 ms - 1234

执行顺序

中间件按注册顺序执行：

javascript
app.use((req, res, next) => {
  console.log('中间件 1');
  next();
});

app.use((req, res, next) => {
  console.log('中间件 2');
  next();
});

app.get('/', (req, res) => {
  console.log('路由处理');
  res.send('Hello');
});

访问 /，输出：

text
中间件 1
中间件 2
路由处理

顺序很重要。比如：

  • express.json() 必须在读取 req.body 的路由之前注册，否则 req.body 是 undefined。
  • express.static() 通常放在路由之前，让静态文件优先命中。
  • 404 中间件必须在所有路由之后。
  • 错误处理中间件必须在所有中间件和路由之后。

路由级中间件

中间件也可以只作用于某个路由：

javascript
function checkAuth(req, res, next) {
  const token = req.headers.authorization;
  if (token === 'secret') return next();
  res.status(401).json({ error: '未授权' });
}

app.get('/api/admin', checkAuth, (req, res) => {
  res.json({ message: '管理员数据' });
});

请求先经过 checkAuth，通过后才进入处理函数。这就是“路由级中间件”。

错误处理中间件

错误处理中间件有四个参数：

javascript
app.use((err, req, res, next) => {
  console.error(err);
  res.status(500).json({ error: '服务器内部错误' });
});

Express 通过参数个数判断它是不是错误处理中间件。四个参数一个都不能少，即使你不用 next，也要写出来：

javascript
app.use((err, req, res, next) => { ... }); // 正确
app.use((err, req, res) => { ... });       // 错误：会被当成普通中间件

在路由里调用 next(err)，就会跳过后面的普通中间件，直接进入错误处理中间件：

javascript
app.get('/api/error', (req, res, next) => {
  next(new Error('测试错误'));
});

内置中间件

Express 4 内置了几个常用中间件：

javascript
app.use(express.json({ limit: '100kb' }));                 // 解析 JSON 请求体
app.use(express.urlencoded({ extended: false, limit: '100kb' })); // 解析表单请求体
app.use(express.static('public'));                        // 静态文件

express.json() 解析 Content-Type: application/json 的请求体，解析结果放在 req.body。如果 JSON 格式错误，它会抛出一个带 status: 400 的错误，交给错误中间件。

express.urlencoded() 解析 application/x-www-form-urlencoded，也就是 HTML 表单默认的提交格式。页面表单能拿到 req.body.title，靠的就是它。

express.static('public') 把 public/ 目录暴露成静态资源。public/styles.css 可以通过 /styles.css 访问，public/logo.png 可以通过 /logo.png 访问。静态中间件通常放在路由之前，但如果你希望 API 路由优先，也可以放在 API 路由之后。

8.5 应用与启动分离

很多教程把 app.listen() 直接写在 app.js 里。项目小的时候没问题，但测试时会很麻烦：测试要启动整个应用，必须占用 3000 端口；如果开发服务器也在跑，就冲突了。

更好的做法是把“创建应用”和“启动服务”分开：

src/app.js：

javascript
function createApp({ todoService, config }) {
  const app = express();
  // 配置中间件、路由
  return app;
}

module.exports = { createApp };

src/server.js：

javascript
const app = createApp({ todoService, config });
app.listen(config.port, () => {
  console.log(`服务已启动：http://localhost:${config.port}`);
});

测试里可以这样：

javascript
const app = createApp({ todoService, config: { env: 'test' } });
const server = app.listen(0); // 0 表示随机端口

server.address().port 拿到实际端口，测试结束后 server.close()。这样测试不会和开发服务器抢端口，也不会互相污染数据。

这是本书最终项目采用的结构。你在 src/app.js 里看不到 listen，在 src/server.js 里看不到路由定义，各自职责清楚。

8.6 asyncHandler：让 async 错误自动进中间件

Express 4 不会自动捕获 async 函数返回的 rejected Promise。看这个路由：

javascript
app.get('/api/todos', async (req, res) => {
  const todos = await todoService.getAll(); // 如果这里抛错
  res.json(todos);                          // 不会执行
});

错误会变成一个未处理的 Promise rejection，请求挂起，浏览器一直等。解决办法有两种：

方案一：每个路由写 try/catch。

javascript
app.get('/api/todos', async (req, res, next) => {
  try {
    res.json(await todoService.getAll());
  } catch (err) {
    next(err);
  }
});

方案二：用一个包装器。

src/utils/asyncHandler.js：

javascript
function asyncHandler(fn) {
  return function wrapped(req, res, next) {
    Promise.resolve(fn(req, res, next)).catch(next);
  };
}

module.exports = { asyncHandler };

使用：

javascript
router.get('/', asyncHandler(async (req, res) => {
  res.json(await todoService.getAll(req.query));
}));

包装器把 async 函数的 rejection 转成 next(err)，错误就能进入统一错误中间件。最终项目采用方案二，路由代码更干净。

Express 5 已经支持自动捕获 async 错误，不需要包装器。但书里用 Express 4，而且理解 next(err) 的机制比依赖框架版本更重要。

8.7 统一错误处理

最终项目的错误处理分两层：路由层决定“错误怎么产生”，错误中间件决定“错误怎么返回”。

src/middleware/errorHandler.js：

javascript
function notFound(req, res, next) {
  next(new NotFoundError('页面或接口不存在'));
}

function errorHandler(err, req, res, next) {
  if (res.headersSent) return next(err);

  const status = Number.isInteger(err.status) ? err.status : 500;
  const isApiRequest = req.originalUrl.startsWith('/api/');

  if (isApiRequest) {
    const message = status < 500 ? err.message : '服务器内部错误';
    return res.status(status).json({
      error: message,
      ...(err.code ? { code: err.code } : {})
    });
  }

  if (status >= 500) console.error('未处理的服务器错误：', err);

  return res.status(status).render('error', {
    title: status === 404 ? '页面不存在' : '出错了',
    status,
    message: status < 500 ? err.message : '服务器内部错误，请稍后重试'
  });
}

几个细节：

  • res.headersSent：如果响应已经开始发送，不能再 res.json 或 render，只能交给默认错误处理。
  • req.originalUrl.startsWith('/api/')：API 请求返回 JSON，页面请求渲染 HTML。同一个错误，对不同客户端要有不同的表现。
  • status < 500 才暴露消息。500 的详细错误只写日志，不返回给用户。
  • 404 也走错误中间件，这样 API 和页面都能统一处理。

src/app.js 里注册顺序：

javascript
app.use('/api/todos', createTodosApiRouter({ todoService }));
app.use('/', createPagesRouter({ todoService }));

app.use(notFound);       // 所有路由之后
app.use(errorHandler);   // 最后

8.8 最终 app.js

下面是最终项目的 src/app.js 核心结构（完整代码见配套项目）：

javascript
const path = require('path');
const express = require('express');
const morgan = require('morgan');

const { createTodosApiRouter } = require('./routes/todosApi');
const { createPagesRouter } = require('./routes/pages');
const { notFound, errorHandler } = require('./middleware/errorHandler');

function createApp({ todoService, config }) {
  const app = express();
  const env = config.env || 'development';

  app.disable('x-powered-by');
  app.set('view engine', 'ejs');
  app.set('views', path.join(__dirname, '..', 'views'));

  if (env !== 'test') {
    app.use(morgan('dev'));
  }

  app.use((req, res, next) => {
    res.setHeader('X-Content-Type-Options', 'nosniff');
    res.setHeader('X-Frame-Options', 'DENY');
    res.setHeader('Referrer-Policy', 'no-referrer');
    next();
  });

  app.use(express.json({ limit: '100kb' }));
  app.use(express.urlencoded({ extended: false, limit: '100kb' }));
  app.use(express.static(path.join(__dirname, '..', 'public')));

  app.get('/api/health', (req, res) => {
    res.json({
      status: 'ok',
      store: config.store || 'json',
      timestamp: new Date().toISOString()
    });
  });

  app.use('/api/todos', createTodosApiRouter({ todoService }));
  app.use('/', createPagesRouter({ todoService }));

  app.use(notFound);
  app.use(errorHandler);

  return app;
}

module.exports = { createApp };

app.disable('x-powered-by') 移除 X-Powered-By: Express 响应头，减少暴露技术栈的信息。这不是强安全措施，但是个好习惯。

三个安全响应头：

  • X-Content-Type-Options: nosniff：禁止浏览器猜测 MIME 类型。
  • X-Frame-Options: DENY：禁止页面被嵌入 iframe，防点击劫持。
  • Referrer-Policy: no-referrer：不把来源 URL 发给外部站点。

更完整的安全头可以用 helmet 中间件，第 11 章会提。

8.9 API 路由

src/routes/todosApi.js：

javascript
const express = require('express');
const { asyncHandler } = require('../utils/asyncHandler');

function createTodosApiRouter({ todoService }) {
  const router = express.Router();

  router.get('/', asyncHandler(async (req, res) => {
    const todos = await todoService.getAll({
      status: req.query.status,
      q: req.query.q
    });
    res.json(todos);
  }));

  router.post('/', asyncHandler(async (req, res) => {
    const todo = await todoService.create(req.body || {});
    res.status(201)
      .location(`/api/todos/${todo.id}`)
      .json(todo);
  }));

  router.patch('/:id/toggle', asyncHandler(async (req, res) => {
    res.json(await todoService.toggle(req.params.id));
  }));

  router.get('/:id', asyncHandler(async (req, res) => {
    res.json(await todoService.getById(req.params.id));
  }));

  router.put('/:id', asyncHandler(async (req, res) => {
    res.json(await todoService.update(req.params.id, req.body || {}));
  }));

  router.delete('/:id', asyncHandler(async (req, res) => {
    res.json(await todoService.remove(req.params.id));
  }));

  return router;
}

注意 patch('/:id/toggle') 放在 /:id 之前。虽然方法不同（PATCH vs GET/PUT/DELETE），路径匹配上不会冲突，但把更具体的路由放在前面是好习惯。

res.status(201).location(...).json(...) 是链式调用：设置状态码、Location 头、发送 JSON，一行完成。

8.11 常见坑

请求一直挂起

中间件里既没有 next()，也没有 res.send()。检查每个中间件是否都有出口。

req.body 是 undefined

  • 没有注册 express.json() 或 express.urlencoded()。
  • 注册顺序在路由之后。
  • 请求的 Content-Type 不对。express.json() 只解析 application/json，表单要 application/x-www-form-urlencoded。

错误没有返回 JSON

  • 错误中间件写成了三个参数，被当成普通中间件。
  • 错误中间件注册在路由之前。
  • async 路由没有 try/catch 或 asyncHandler，错误没有进入 next(err)。

静态文件 404

  • express.static 的路径不对。用 path.join(__dirname, '..', 'public') 拼绝对路径。
  • 静态中间件放在了一个匹配所有路径的路由之后，请求被前面的路由拦截了。
  • 文件名大小写不对。Linux 区分大小写。

或者修改 PORT。

9.1 为什么还需要服务端渲染

现在项目已经有完整的 API 了。用 curl 或 Postman 能增删改查，为什么还要做页面？

因为 API 是给程序用的。一个不会用命令行的用户，打开浏览器只看到一串 JSON，没法完成“添加一条待办”这件事。页面是把 API 的能力翻译成人能理解、能点击的界面。

前端页面有两条路线：

路线一：服务端渲染（SSR）。 服务器把数据拼成 HTML，浏览器直接显示。用户提交表单，服务器处理完再返回新页面。Express + EJS 就是这条路线。

路线二：前后端分离（SPA）。 服务器只返回 JSON，浏览器用 React/Vue 渲染页面，用 fetch 调 API。这是现代前端的主流。

本书选路线一，原因很实际：

  • 不需要学 React/Vue，不需要构建工具，不需要处理前端路由。
  • 表单、链接、重定向都是浏览器原生能力，代码少，出错点少。
  • 服务端渲染的页面天然对 SEO 友好，首屏快。
  • 教学重点在后端：路由、中间件、数据层、错误处理。页面只是把这些能力展示出来。

等你把这一章做完，再回头看路线二，你会发现 SPA 只是把“渲染”和“请求”搬到了浏览器，后端要做的事并没有变。

9.3 EJS 语法

EJS 的语法只有四种标签：

标签 作用 例子
<%= 表达式 %> 输出并 HTML 转义 <%= todo.title %>
<%- 表达式 %> 输出但 不转义 <%- html %>（慎用）
<% 代码 %> 执行 JavaScript，不输出 <% if (x) { %>
<%# 注释 %> 注释 <%# 这是注释 %>

一个例子：

ejs
<h1><%= title %></h1>

<% if (items.length === 0) { %>
  <p>暂无待办</p>
<% } else { %>
  <ul>
    <% items.forEach(function (item) { %>
      <li class="<%= item.completed ? 'done' : '' %>">
        <%= item.title %>
      </li>
    <% }); %>
  </ul>
<% } %>

转义：EJS 最重要的安全特性

假设有一条待办的标题是：

html
<script>alert('xss')</script>

用 <%= item.title %> 输出，EJS 会转义成：

html
&lt;script&gt;alert('xss')&lt;/script&gt;

浏览器把它当普通文字显示，不会执行脚本。

如果用 <%- item.title %>，脚本会被原样插入页面，浏览器执行它。这就是 XSS（跨站脚本攻击）。

规则很简单：只要内容是用户输入的，一律用 <%=。 只有你完全信任、确实需要渲染 HTML 的内容（比如自己写的富文本），才用 <%-，并且要先做 sanitize。

模板里不要写太多逻辑

EJS 允许写任意 JavaScript，但不要把业务逻辑塞进模板。模板只负责“展示”：

  • 数据准备、排序、过滤、统计，在路由/业务层完成。
  • 模板里只做简单的条件判断和循环。
  • 复杂的格式化，写成辅助函数，通过 app.locals 传进去。

最终项目在 app.js 里注册了一个日期格式化函数：

javascript
app.locals.formatDate = (value) => {
  if (!value) return '';
  const date = new Date(value);
  if (Number.isNaN(date.getTime())) return '';
  return date.toLocaleString('zh-CN', { hour12: false });
};

模板里直接 <%= formatDate(item.createdAt) %>。这样模板干净，格式化逻辑可测试、可复用。

9.5 页面路由与 PRG 模式

页面路由在 src/routes/pages.js。核心是四个表单处理函数：

javascript
router.post('/todos/add', asyncHandler(async (req, res) => {
  try {
    await todoService.create({ title: req.body.title });
    redirectWithNotice(res, '已添加一条待办');
  } catch (err) {
    redirectWithError(res, err);
  }
}));

redirectWithNotice / redirectWithError 都是重定向：

javascript
function redirectWithError(res, err) {
  const message = err && err.expose ? err.message : '操作失败，请稍后重试';
  res.redirect(303, `/todos?error=${encodeURIComponent(message)}`);
}

function redirectWithNotice(res, message) {
  res.redirect(303, `/todos?notice=${encodeURIComponent(message)}`);
}

这就是 PRG（Post/Redirect/Get）模式：

  1. 用户 POST 提交表单。
  2. 服务器处理完，返回 303 重定向到 GET /todos。
  3. 浏览器跟随重定向，GET 新页面。

为什么不在 POST 里直接 render？因为用户刷新页面时，浏览器会重复提交上一次的 POST，导致重复添加。重定向后，地址栏是 GET 请求，刷新只是重新拉列表，不会重复写入。

303 See Other 明确告诉浏览器“用 GET 访问新地址”，比 302 更语义化。浏览器对 303 的支持很好。

错误处理：页面和 API 不一样

API 出错返回 JSON：

json
{ "error": "待办不存在", "code": "NOT_FOUND" }

页面出错不能返回 JSON，用户看不懂。页面路由的做法是：捕获业务错误，重定向回列表，把错误消息放在查询参数里：

text
/todos?error=待办不存在

列表页读取 req.query.error，渲染成红色提示条：

ejs
<% if (error) { %>
  <div class="banner banner-error" role="alert"><%= error %></div>
<% } %>

注意 error 来自 URL，仍然要用 <%= 转义，防止有人构造 /todos?error=<script>... 进行 XSS。

GET /todos 的数据准备

javascript
router.get('/todos', asyncHandler(async (req, res) => {
  const status = ['all', 'active', 'completed'].includes(req.query.status)
    ? req.query.status
    : 'all';
  const q = typeof req.query.q === 'string' ? req.query.q.trim().slice(0, 100) : '';

  const [items, stats] = await Promise.all([
    todoService.getAll({ status, q }),
    todoService.getStats()
  ]);

  res.render('list', {
    title: '我的待办',
    items,
    stats,
    filters: { status, q },
    error: typeof req.query.error === 'string' ? req.query.error.slice(0, 200) : null,
    notice: typeof req.query.notice === 'string' ? req.query.notice.slice(0, 200) : null
  });
}));

几个防御性处理：

  • status 只接受三个白名单值，非法值回退到 all，避免业务层抛错导致页面 400。
  • q 只接受字符串，截断到 100 字符，避免超长查询。
  • error / notice 截断到 200 字符，避免 URL 过长或恶意内容撑爆页面。
  • Promise.all 并发获取列表和统计，减少等待时间。

9.8 常见问题

模板找不到：Failed to lookup view "list"

  • views 目录路径不对。用 path.join(__dirname, '..', 'views')。
  • 文件名不是 list.ejs。
  • app.set('view engine', 'ejs') 没写。

表单提交后 req.body 是 undefined

  • 没注册 express.urlencoded({ extended: false })。
  • 注册在路由之后。
  • 表单的 method 不是 POST，或者 name 属性拼错。

提交后页面没变化

  • 路由里没有 res.redirect，或者重定向路径写错。
  • 数据库/文件写入失败，但错误被吞了。
  • 浏览器缓存了旧页面。强制刷新 Ctrl + F5。

样式不生效

  • express.static 路径不对。
  • <link> 的 href 写成了相对路径，在 /todos/1 这类路径下会解析错。用 /styles.css 绝对路径。
  • 浏览器缓存。开发者工具里勾选 Disable cache。

中文乱码

  • HTML 有 <meta charset="UTF-8">。
  • 响应头有 charset=utf-8（res.render 会自动设置）。
  • 数据文件/数据库是 UTF-8。

10.1 JSON 文件不够用了

第 6 章的 JSON 存储能持久化，但它有两个明显的问题。

第一，每次读写都要操作整个文件。 哪怕只想查一条待办，也要把整个 JSON 读进来、JSON.parse 成数组、再 find。数据量到几万条时，内存和 CPU 都会吃不消。

第二，不支持复杂查询。 想查“所有未完成的待办，按创建时间倒序，只取前 20 条”，必须先读全量，再用 JavaScript 过滤、排序、截取。分页、聚合、模糊搜索都变得很笨重。

数据库就是为这些问题设计的。MySQL 是最流行的关系型数据库之一，学校环境、企业项目里都非常常见。它把数据存在表里，用 SQL 查询，支持索引、事务、并发控制。

JSON 文件 MySQL
数据单位：整个文件 表（table）
数据行：数组元素 行（row）
字段：对象属性 列（column）
主键：手动生成 AUTO_INCREMENT 自增
查询：读全量再过滤 SQL 条件查询、索引
并发：容易冲突 事务、锁、连接池

一条待办在 MySQL 里长这样：

id title completed created_at
1 学习 MySQL 0 2026-10-09 08:00:00
2 完成项目 1 2026-10-09 09:00:00

completed 用 0/1 表示布尔值，created_at 记录创建时间。

10.3 建库建表

登录 MySQL：

bash
mysql -u root -p

执行：

sql
CREATE DATABASE IF NOT EXISTS todo_app
  DEFAULT CHARACTER SET utf8mb4
  COLLATE utf8mb4_unicode_ci;

USE todo_app;

CREATE TABLE IF NOT EXISTS todos (
  id INT UNSIGNED NOT NULL AUTO_INCREMENT,
  title VARCHAR(255) NOT NULL,
  completed TINYINT(1) NOT NULL DEFAULT 0,
  created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
    ON UPDATE CURRENT_TIMESTAMP(3),
  PRIMARY KEY (id),
  KEY idx_todos_completed_created (completed, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

INSERT INTO todos (title, completed) VALUES
  ('学习 Node.js', 0),
  ('完成项目立项', 1),
  ('复习 MySQL', 0);

SELECT * FROM todos;

字段解释

  • id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY：无符号整数，自增主键。UNSIGNED 表示不允许负数，范围更大。
  • title VARCHAR(255) NOT NULL：可变长度字符串，最多 255 个字符，不能为空。
  • completed TINYINT(1) NOT NULL DEFAULT 0：MySQL 的 BOOLEAN 是 TINYINT(1) 的别名，0 表示 false，1 表示 true。
  • created_at DATETIME(3) DEFAULT CURRENT_TIMESTAMP(3)：创建时自动填入当前时间，保留 3 位毫秒。
  • updated_at DATETIME(3) ... ON UPDATE CURRENT_TIMESTAMP(3)：每次更新行时自动刷新。这样即使业务代码忘了写 updated_at，数据库也会维护。
  • KEY idx_todos_completed_created (completed, created_at)：联合索引，加速“按完成状态筛选 + 按创建时间排序”的查询。
  • ENGINE=InnoDB：支持事务、行锁、外键。
  • CHARSET=utf8mb4：支持中文、emoji 和四字节字符。不要用 utf8（MySQL 的 utf8 最多 3 字节，emoji 会报错）。

为什么时间用 UTC

created_at 存的是 UTC 时间，不是本地时间。这样服务器迁移到不同时区，数据不会错乱。展示时再转成本地时区。

在 Node.js 里，我们通过 mysql2 的 timezone: 'Z' 告诉驱动“数据库里的时间按 UTC 解释”，读取出来就是正确的 Date 对象，再 toISOString() 返回给前端。

用脚本初始化

scripts/init-db.js：

javascript
const mysql = require('mysql2/promise');
const config = require('../src/config');

async function main() {
  const { database } = config.db;
  if (!/^[A-Za-z0-9_]+$/.test(database)) {
    throw new Error('DB_NAME 只能包含字母、数字和下划线');
  }

  const connection = await mysql.createConnection({
    host: config.db.host,
    port: config.db.port,
    user: config.db.user,
    password: config.db.password
  });

  try {
    await connection.query(
      `CREATE DATABASE IF NOT EXISTS \`${database}\`
       DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`
    );
    await connection.changeUser({ database });
    await connection.query(`
      CREATE TABLE IF NOT EXISTS todos (
        id INT UNSIGNED NOT NULL AUTO_INCREMENT,
        title VARCHAR(255) NOT NULL,
        completed TINYINT(1) NOT NULL DEFAULT 0,
        created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
        updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
          ON UPDATE CURRENT_TIMESTAMP(3),
        PRIMARY KEY (id),
        KEY idx_todos_completed_created (completed, created_at)
      ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
    `);
    console.log(`数据库 ${database} 与 todos 表已就绪。`);
  } finally {
    await connection.end();
  }
}

main().catch((err) => {
  console.error('初始化数据库失败：', err.message);
  process.exit(1);
});

DB_NAME 不能直接拼进 SQL（即使用了反引号）。脚本先校验只允许字母、数字、下划线，再拼接。这叫“标识符白名单”，是动态表名/库名时的基本安全措施。

bash
npm install mysql2

使用 mysql2/promise，它支持 async/await。

src/db.js：

javascript
const mysql = require('mysql2/promise');

function createPool(dbConfig) {
  return mysql.createPool({
    host: dbConfig.host,
    port: dbConfig.port,
    user: dbConfig.user,
    password: dbConfig.password,
    database: dbConfig.database,
    waitForConnections: true,
    connectionLimit: 10,
    queueLimit: 0,
    charset: 'utf8mb4',
    timezone: 'Z',
    decimalNumbers: true
  });
}

async function testConnection(pool) {
  const connection = await pool.getConnection();
  try {
    await connection.ping();
  } finally {
    connection.release();
  }
}

module.exports = { createPool, testConnection };

为什么用连接池

每次查询都新建一个 MySQL 连接，需要 TCP 握手、身份认证、会话初始化，开销很大。连接池提前创建一组连接，用完放回池子，下次复用。

  • connectionLimit: 10：最多 10 个并发连接。太小会排队，太大会压垮数据库。教学项目 10 足够。
  • waitForConnections: true：连接用完时，新请求排队等待，而不是直接报错。
  • queueLimit: 0：排队数量不限制。生产环境可以设一个上限，避免无限堆积。
  • charset: 'utf8mb4'：和数据库字符集保持一致。
  • timezone: 'Z'：按 UTC 解释 DATETIME。
  • decimalNumbers: true：把 DECIMAL 转成 JavaScript 数字，而不是字符串（统计时会用到）。

10.5 CRUD：占位符是底线

先看一段错误的代码：

javascript
const sql = `SELECT * FROM todos WHERE id = ${id}`;
await pool.query(sql);

如果 id 是用户传入的 1 OR 1=1，SQL 变成：

sql
SELECT * FROM todos WHERE id = 1 OR 1=1

返回所有数据。更糟的是，攻击者可以拼接 UNION SELECT、DROP TABLE，这就是 SQL 注入。

正确写法：

javascript
const [rows] = await pool.execute(
  'SELECT * FROM todos WHERE id = ?',
  [id]
);

? 是占位符，pool.execute 会把它作为参数传给数据库，由数据库负责转义。参数永远被当成“值”，不会被当成 SQL 代码。

三条规则：

  1. 所有用户输入都用 ? 占位符。 包括 id、标题、状态、搜索词。
  2. 列名、表名不能直接用占位符。 如果必须动态拼接，只能用代码里的白名单，不能来自用户输入。
  3. 不要用字符串模板拼 SQL。 即使你觉得“这个值肯定是数字”，也不要。防御要在每一层都做。

查询

javascript
async function getAll({ status = 'all', q = '' } = {}) {
  const where = [];
  const params = [];

  if (status === 'active') where.push('completed = 0');
  if (status === 'completed') where.push('completed = 1');
  if (q) {
    where.push('LOCATE(?, title) > 0');
    params.push(q);
  }

  const sql = `
    SELECT id, title, completed, created_at, updated_at
    FROM todos
    ${where.length > 0 ? `WHERE ${where.join(' AND ')}` : ''}
    ORDER BY created_at DESC, id DESC
  `;

  const [rows] = await pool.execute(sql, params);
  return rows.map(mapRow);
}

LOCATE(?, title) > 0 等价于“标题包含关键词”，但不需要处理 %、_ 这些 LIKE 通配符。如果要用 LIKE，记得转义：

javascript
const keyword = q.replace(/[\\%_]/g, '\\$&');
where.push("title LIKE ? ESCAPE '\\\\'");
params.push(`%${keyword}%`);

LOCATE 更简单，教学项目用它就够了。数据量大时，LIKE '%关键词%' 无法使用普通索引，需要考虑全文索引或搜索引擎。

单条查询

javascript
async function getById(id) {
  const [rows] = await pool.execute(
    `SELECT id, title, completed, created_at, updated_at
     FROM todos WHERE id = ?`,
    [id]
  );
  return rows.length > 0 ? mapRow(rows[0]) : null;
}

pool.execute 返回 [rows, fields]。rows 是结果数组，fields 是列元数据（通常不需要）。

创建

javascript
async function create({ title }) {
  const [result] = await pool.execute(
    `INSERT INTO todos (title, completed, created_at, updated_at)
     VALUES (?, 0, UTC_TIMESTAMP(3), UTC_TIMESTAMP(3))`,
    [title]
  );
  return getById(result.insertId);
}

INSERT 返回的 result 包含：

  • insertId：自增主键。
  • affectedRows：影响行数。

用 insertId 再查一次，返回完整的对象（包括数据库生成的 created_at）。这样接口返回的字段和查询接口一致。

更新

javascript
async function update(id, patch) {
  const fields = [];
  const params = [];

  if (patch.title !== undefined) {
    fields.push('title = ?');
    params.push(patch.title);
  }
  if (patch.completed !== undefined) {
    fields.push('completed = ?');
    params.push(patch.completed ? 1 : 0);
  }

  if (fields.length > 0) {
    fields.push('updated_at = UTC_TIMESTAMP(3)');
    params.push(id);
    await pool.execute(
      `UPDATE todos SET ${fields.join(', ')} WHERE id = ?`,
      params
    );
  }

  return getById(id);
}

动态 SET 子句的列名来自代码里的固定字符串（title = ?、completed = ?），不是用户输入，所以安全。值全部走 params。

patch.completed ? 1 : 0 把布尔值转成 MySQL 的 TINYINT。虽然 mysql2 通常能自动转换布尔值，显式转换更清楚。

删除

javascript
async function remove(id) {
  const todo = await getById(id);
  if (!todo) return null;
  await pool.execute('DELETE FROM todos WHERE id = ?', [id]);
  return todo;
}

先查再删，是为了返回被删除的对象。业务层已经用 getById 检查过存在性，这里的 getById 是双重保险。

10.6 字段映射：snake_case 到 camelCase

数据库列名用下划线（created_at），JavaScript 对象用驼峰（createdAt）。这是两种社区的命名习惯，没有对错，但要在边界处转换。

javascript
function mapRow(row) {
  return {
    id: row.id,
    title: row.title,
    completed: Boolean(row.completed),
    createdAt: toIsoString(row.created_at),
    updatedAt: toIsoString(row.updated_at)
  };
}

toIsoString 处理 Date 和字符串：

javascript
function toIsoString(value) {
  if (!value) return null;
  if (value instanceof Date) return value.toISOString();
  const date = new Date(value);
  return Number.isNaN(date.getTime()) ? null : date.toISOString();
}

为什么要映射，不直接在 SQL 里 SELECT created_at AS createdAt？两种做法都可以。映射函数更集中：加字段、改类型、做兼容，只改一个地方；SQL 别名散落在每个查询里，容易漏。而且 mapRow 可以单独测试。

10.7 统计

javascript
async function getStats() {
  const [rows] = await pool.execute(
    `SELECT
       COUNT(*) AS total,
       SUM(CASE WHEN completed = 1 THEN 1 ELSE 0 END) AS completed
     FROM todos`
  );
  const total = Number(rows[0].total) || 0;
  const completed = Number(rows[0].completed) || 0;
  return { total, completed, active: total - completed };
}

COUNT(*) 返回字符串或数字（取决于驱动配置），SUM 在没有匹配行时返回 null。用 Number(...) || 0 兜底。

这比“查出所有数据再在 JavaScript 里数”快得多：数据库只返回一行聚合结果，不用把全部数据传到应用层。

数据库没创建。运行 npm run db:init，或手动执行 CREATE DATABASE。

Table 'todo_app.todos' doesn't exist

表没创建。db:init 会建表；如果手动建库，别忘了执行 CREATE TABLE。

中文乱码 / emoji 报错

  • 数据库和表用 utf8mb4。
  • 连接配置 charset: 'utf8mb4'。
  • 列用 utf8mb4 排序规则。
  • 不要用 utf8（三字节）。

时间差了 8 小时

  • 数据库存 UTC，连接配置 timezone: 'Z'。
  • 展示时用 toLocaleString('zh-CN') 转本地时区。
  • 不要混用 NOW() 和 UTC_TIMESTAMP()。本书统一用 UTC_TIMESTAMP(3)。

affectedRows 是 0，但数据明明存在

MySQL 默认返回“实际改变的行数”。如果更新的值和原值相同，affectedRows 可能是 0。不要用 affectedRows === 0 判断“记录不存在”，先 getById 检查。

第 5 章提过：toggle 是“先读再写”，两个请求可能都读到旧状态。解决办法：

sql
UPDATE todos
SET completed = NOT completed, updated_at = UTC_TIMESTAMP(3)
WHERE id = ?

一条原子 SQL 完成切换，不依赖应用层读到的旧值。这是数据库相对于 JSON 文件的优势之一。

这一章不引入新框架，只做“打磨”。打磨的目标不是“更多功能”，而是更少的意外。

11.2 错误处理：让每种错误都有归宿

先建立一个错误分类表：

场景 错误类型 HTTP 状态码 用户看到
标题为空 ValidationError 400 “标题不能为空”
id 不是正整数 ValidationError 400 “无效的ID格式”
completed 不是布尔值 ValidationError 400 “completed 必须是布尔值”
待办不存在 NotFoundError 404 “待办不存在”
接口不存在 NotFoundError 404 “页面或接口不存在”
JSON 格式错误 Express 抛出的 400 400 “请求体不是合法 JSON”
请求体太大 Express 抛出的 413 413 “请求体太大”
数据库连接失败 原生 Error 500 “服务器内部错误”
未预期异常 原生 Error 500 “服务器内部错误”

这张表是错误处理的“合同”。路由层负责抛出正确的错误类型，错误中间件负责把它翻译成正确的响应。

API 与页面分开

同一个错误，API 和页面的表现不同：

  • API：返回 JSON，带 error 和 code，前端/脚本可以判断。
  • 页面：渲染错误页，或者重定向回列表并显示提示。

src/middleware/errorHandler.js 已经做了这个判断：

javascript
const isApiRequest = req.originalUrl.startsWith('/api/');

if (isApiRequest) {
  const message = status < 500 ? err.message : '服务器内部错误';
  return res.status(status).json({
    error: message,
    ...(err.code ? { code: err.code } : {})
  });
}

return res.status(status).render('error', {
  title: status === 404 ? '页面不存在' : '出错了',
  status,
  message: status < 500 ? err.message : '服务器内部错误，请稍后重试'
});

这里有一个容易忽略的点：页面表单的错误，不应该走全局错误页。 用户在 /todos 添加一条空标题，你把他带到一个冷冰冰的“400 出错了”页面，体验很差。更好的做法是重定向回列表，在表单上方显示“标题不能为空”。

所以页面路由单独 try/catch：

javascript
router.post('/todos/add', asyncHandler(async (req, res) => {
  try {
    await todoService.create({ title: req.body.title });
    redirectWithNotice(res, '已添加一条待办');
  } catch (err) {
    redirectWithError(res, err);
  }
}));

全局错误页只处理“页面本身不存在”“渲染失败”“未预期异常”这类情况。错误处理要分场景，不能一刀切。

错误页

views/error.ejs：

ejs
<main class="shell">
  <section class="panel error-panel">
    <p class="error-code"><%= status %></p>
    <h1><%= title %></h1>
    <p class="error-message"><%= message %></p>
    <a class="btn btn-primary" href="/todos">返回待办列表</a>
  </section>
</main>

错误页不显示堆栈、不显示 SQL、不显示文件路径。堆栈只写服务器日志。用户需要的是“发生了什么、下一步去哪”，不是你的调用栈。

404 也要有出口

notFound 中间件放在所有路由之后：

javascript
app.use(notFound);
app.use(errorHandler);

访问 /not-exists，API 返回 JSON，页面渲染错误页。不要留下 Express 默认的 Cannot GET /not-exists，那会让项目看起来没做完。

11.3 校验：三层一致

校验要在三个地方保持一致：

  1. HTML 层：required、maxlength、type。提升体验，但可以被绕过。
  2. 业务层：normalizeTitle、normalizeId、类型检查。真正的防线。
  3. 数据库层：NOT NULL、VARCHAR(255)、TINYINT(1)。最后一道保险。

标题

javascript
function normalizeTitle(value) {
  if (typeof value !== 'string') {
    throw new ValidationError('标题必须是字符串');
  }
  const title = value.trim();
  if (!title) throw new ValidationError('标题不能为空');
  if (title.length > 255) {
    throw new ValidationError('标题不能超过 255 个字符');
  }
  return title;
}

trim() 很重要。用户输入 " "，required 会认为有值，但业务层必须拒绝。用户输入 " 学习 "，应该存成 "学习"，而不是带一堆空格。

id

javascript
function normalizeId(value) {
  const id = typeof value === 'string' ? Number(value) : value;
  if (!Number.isInteger(id) || id <= 0) {
    throw new ValidationError('无效的ID格式');
  }
  return id;
}

不要用 parseInt。parseInt('12abc') 得到 12，把非法输入变成了合法 id。Number('12abc') 是 NaN，会被拒绝。

completed

javascript
if (patch.completed !== undefined) {
  if (typeof patch.completed !== 'boolean') {
    throw new ValidationError('completed 必须是布尔值');
  }
  safePatch.completed = patch.completed;
}

不要接受 'true'、1、'yes' 这些“看起来像布尔”的值。API 的契约是 JSON 布尔值，就严格按布尔值校验。页面表单不需要传 completed，它走 /toggle 路由。

只允许白名单字段

javascript
const safePatch = {};
if (patch.title !== undefined) safePatch.title = normalizeTitle(patch.title);
if (patch.completed !== undefined) {
  if (typeof patch.completed !== 'boolean') {
    throw new ValidationError('completed 必须是布尔值');
  }
  safePatch.completed = patch.completed;
}

用户传 { id: 999, createdAt: '2000-01-01', title: 'x' }，只有 title 会进入 safePatch。id 和 createdAt 被忽略，不能通过更新接口篡改。

这就是“批量赋值（mass assignment）”防护。很多安全漏洞不是因为 SQL 注入，而是因为“用户传什么，代码就更新什么”。

请求体大小

javascript
app.use(express.json({ limit: '100kb' }));
app.use(express.urlencoded({ extended: false, limit: '100kb' }));

限制请求体大小，防止有人发一个 100MB 的 JSON 把内存撑爆。100KB 对 Todo 应用足够。上传文件是另一套机制，不在本期范围。

11.4 安全：把门锁上

1. 不要提交密码

.gitignore：

gitignore
.env

.env.example 只放模板：

ini
DB_PASSWORD=你的密码

代码里不要写：

javascript
password: '123456' // 千万不要

用 process.env.DB_PASSWORD。部署时通过环境变量注入，而不是把 .env 传到服务器上。

2. SQL 注入

所有 SQL 用 ? 占位符。第 10 章已经讲过。再强调一次：不要用模板字符串拼接用户输入。

3. XSS

EJS 模板一律用 <%= 输出用户内容。不要用 <%-，除非你明确知道内容已经 sanitize。

如果将来要支持富文本（比如博客正文），需要引入 sanitize-html 之类的库，白名单允许的标签和属性。不要自己写正则过滤 HTML，那几乎一定会漏。

4. CSRF

CSRF（跨站请求伪造）是攻击者诱导已登录用户在不知情的情况下发出请求。它的前提是“浏览器会自动带上凭证（Cookie）”。

本书的项目没有登录、没有 Cookie，所以 CSRF 风险很低。但如果你继续加登录功能，必须做：

  • 表单加 CSRF token，服务端校验。
  • Cookie 设置 SameSite=Lax 或 Strict。
  • 敏感操作（删除、改密码）要求二次确认或重新认证。

不要等到有用户数据了才想起 CSRF。

5. 安全响应头

app.js 里已经加了三个：

javascript
res.setHeader('X-Content-Type-Options', 'nosniff');
res.setHeader('X-Frame-Options', 'DENY');
res.setHeader('Referrer-Policy', 'no-referrer');

更完整的方案是 helmet：

bash
npm install helmet
javascript
const helmet = require('helmet');
app.use(helmet());

helmet 会设置一串安全头，包括 CSP。CSP 可能会阻止内联脚本和内联样式，接入时要根据页面调整。本书为了保持页面简单，没有默认启用；你可以把它作为下一版的安全增强。

6. 速率限制

公开部署的 API 需要防刷。可以用 express-rate-limit：

bash
npm install express-rate-limit
javascript
const rateLimit = require('express-rate-limit');

app.use('/api/', rateLimit({
  windowMs: 60 * 1000,
  max: 60,
  standardHeaders: true,
  message: { error: '请求过于频繁，请稍后再试' }
}));

教学项目不强制，但你要知道这个概念。没有速率限制，一个脚本就能把你的数据库打满。

7. HTTPS

本地开发用 HTTP 没问题。部署到公网必须用 HTTPS。常见做法是 Nginx/Caddy 反向代理，由它们处理证书，Node.js 只监听 127.0.0.1。

如果应用在反向代理后面，要设置：

javascript
app.set('trust proxy', 1);

这样 req.ip、req.protocol 才能拿到真实客户端信息。不要无条件信任所有代理，否则 IP 可以被伪造。

11.5 配置：启动时失败，而不是运行时爆炸

src/config.js 在启动时读取环境变量，并做基本校验：

javascript
const store = (process.env.DATA_STORE || 'json').toLowerCase();
if (!['json', 'mysql'].includes(store)) {
  throw new Error(`DATA_STORE 只能是 json 或 mysql，当前值：${store}`);
}

如果用户写了 DATA_STORE=mysq，启动时立刻报错，而不是等到第一个请求才发现。配置错误要在启动时暴露。

端口也做了处理：

javascript
function toPositiveInt(value, fallback) {
  const n = Number.parseInt(value, 10);
  return Number.isInteger(n) && n > 0 ? n : fallback;
}

port: toPositiveInt(process.env.PORT, 3000)

PORT=abc 会回退到 3000，而不是让 listen(NaN) 报一个看不懂的错。

MySQL 模式下，启动前 ping：

javascript
await store.ping();

数据库连不上，进程退出，日志里写清楚原因。不要让服务“假装健康”。

11.6 体验：细节决定演示效果

操作反馈

每次写操作后，重定向并带上 notice：

text

页面顶部显示绿色提示条。失败时带 error，显示红色提示条。用户知道“刚才那一下到底成没成”。

空状态

空列表不是“什么都不显示”，而是告诉用户下一步做什么：

ejs

删除确认

删除是不可逆操作，必须确认。用 data-confirm + 外部 JS 实现渐进增强：

html

没有 JS 时表单仍能提交；有 JS 时弹确认。不要用 onclick="return confirm(...)" 内联写法，它和 CSP 不兼容，也不好维护。

键盘与屏幕阅读器

  • 每个输入框都有 <label>，即使视觉上隐藏，也要有 for 和 id。
  • 按钮有可读文本，图标按钮加 aria-label。
  • 焦点状态明显：:focus-visible 加轮廓。
  • 错误提示用 role="alert"，屏幕阅读器会朗读。
  • 完成状态不只靠颜色，还加删除线。

移动端

  • viewport meta 标签。
  • 输入框、按钮在窄屏下换行，不横向溢出。
  • 点击区域至少 44×44 像素（删除按钮可以小一点，但要有足够间距）。
  • 统计卡片在手机上改成纵向排列。

这些不是“锦上添花”，而是“能不能用”的底线。

12.1 为什么最后才写测试

你可能会问：为什么不在第 5 章就写测试？

因为测试需要“稳定的接口”。第 5 章之前，数据层还在从内存换到文件、从文件换到数据库，接口天天变，测试写了也要跟着改。等到 v1.1，业务接口稳定了，测试的投入产出比最高。

但这不代表测试是“最后补的作业”。真实项目里，测试应该跟着功能一起写。本书为了教学节奏，把测试集中到最后一章；你以后做项目，可以每完成一个接口就写一条测试。

测试解决三个问题：

  1. 回归。 你改了一个小地方，怎么知道没把别的功能弄坏？
  2. 文档。 测试用例就是“这个接口应该怎么行为”的可执行说明。
  3. 勇气。 有测试兜底，你才敢重构。

12.2 测试金字塔

text
        /\
       /  \      E2E（端到端）：浏览器点击真实页面
      /----\
     /      \    集成测试：HTTP 请求 → 路由 → 业务 → 仓库
    /--------\
   /          \  单元测试：函数、业务规则
  /------------\
  • 单元测试：测一个函数或一个模块，速度快，定位准。比如 normalizeTitle 对空字符串抛错。
  • 集成测试：测多个模块协作，比如发一个 HTTP 请求，验证返回 201、数据库里多了一条。
  • 端到端测试：用浏览器真实点击，最接近用户，但慢、脆、维护成本高。

本书写单元测试和集成测试，不写 E2E。E2E 需要 Playwright/Cypress，是另一本书的内容。对教学项目来说，API 集成测试已经能覆盖大部分风险。

12.4 数据层测试

test/data.test.js 测 JSON 仓库和业务层：

const assert = require('node:assert/strict');
const fs = require('fs/promises');
const os = require('os');
const path = require('path');
const { EventEmitter } = require('events');

const { createJsonTodoRepository } = require('../src/repositories/jsonTodoRepository');
const { createTodoService } = require('../src/data');
const { ValidationError, NotFoundError } = require('../src/errors');

test('JSON 数据层：增删改查、筛选、持久化与事件', async (t) => {
  const dir = await fs.mkdtemp(path.join(os.tmpdir(), 'todo-test-'));
  const file = path.join(dir, 'todos.json');
  t.after(() => fs.rm(dir, { recursive: true, force: true }));

  const bus = new EventEmitter();
  const events = [];
  bus.on('data:created', (payload) => events.push(payload));

  const service = createTodoService(createJsonTodoRepository(file), bus);

  const first = await service.create({ title: '  学习 Node.js  ' });
  assert.equal(first.title, '学习 Node.js');
  assert.equal(events.length, 1);

  const toggled = await service.toggle(first.id);
  assert.equal(toggled.completed, true);

  const completed = await service.getAll({ status: 'completed' });
  assert.deepEqual(completed.map((todo) => todo.id), [first.id]);

  // 换一个仓库实例读同一个文件，验证真的落盘了
  const another = createTodoService(
    createJsonTodoRepository(file),
    new EventEmitter()
  );
  assert.equal((await another.getById(first.id)).title, '学习 Node.js');

  await assert.rejects(() => service.create({ title: '  ' }), ValidationError);
  await assert.rejects(() => service.getById(999), NotFoundError);
});

这段测试有几个关键点：

  • 用临时目录。 fs.mkdtemp(path.join(os.tmpdir(), 'todo-test-')) 在系统临时目录创建唯一文件夹，不污染项目数据。
  • 用 t.after 清理。 测试结束删除临时目录，成功失败都清理。
  • 换实例验证持久化。 同一个文件，新的仓库实例能读到，说明数据真的写进了文件，而不是留在内存。
  • 测试错误路径。 不只测成功，空标题、不存在的 id 都要测。

const { createMemoryTodoRepository } = require('../src/repositories/memoryTodoRepository');
const { createTodoService } = require('../src/data');
const { createApp } = require('../src/app');

test('HTTP API 与页面路由', async (t) => {
  const todoService = createTodoService(
    createMemoryTodoRepository([
      { id: 1, title: '学习 Express', completed: false,
        createdAt: '2026-01-01T08:00:00.000Z',
        updatedAt: '2026-01-01T08:00:00.000Z' }
    ]),
    new EventEmitter()
  );

  const app = createApp({
    todoService,
    config: { env: 'test', store: 'memory' }
  });

  const server = await new Promise((resolve) => {
    const instance = app.listen(0, '127.0.0.1', () => resolve(instance));
  });
  t.after(() => new Promise((resolve) => server.close(resolve)));

  const base = `http://127.0.0.1:${server.address().port}`;

  const response = await fetch(`${base}/api/todos`);
  assert.equal(response.status, 200);
  const todos = await response.json();
  assert.equal(todos.length, 1);
  assert.equal(todos[0].title, '学习 Express');
});

为什么用 app.listen(0)？

  • 0 表示让操作系统分配一个空闲端口，测试不会和开发服务器抢 3000。
  • server.address().port 拿到实际端口。
  • 测试结束 server.close()，释放端口。

为什么用内存仓库？

  • 不依赖 MySQL，npm test 在任何机器上都能跑。
  • 每个测试文件独立，不会互相污染数据。
  • 速度快，毫秒级。

为什么不用 supertest？

supertest 很好用，但它是一个额外依赖。fetch 是 Node.js 18 内置的，足够测 HTTP。少一个依赖，少一份维护成本。你也可以用 supertest，原理一样。

测试要覆盖什么

至少覆盖：

  • 健康检查 200。
  • 列表 200，筛选正确。
  • 创建 201，返回 Location。
  • 单条 200，不存在 404。
  • 更新 200。
  • 切换 200。
  • 删除 200，删除后再查 404。
  • 空标题 400。
  • 非法 id 400。
  • 未知接口 404。
  • 页面 200，包含标题。
  • 表单提交 303，重定向后能看到新数据。
  • 页面 404 渲染错误页。

这些用例在配套项目的 test/api.test.js 里都有。

12.9 部署：从 localhost 到公网

准备

  1. 一台服务器（云主机/VPS），安装 Node.js 18+、MySQL、Nginx。
  2. 把代码拉到服务器，或者用 CI/CD 发布。
  3. 配置生产环境变量。
bash
npm ci --omit=dev

只安装运行依赖，不装 nodemon 等开发依赖。

.env：

ini
NODE_ENV=production
PORT=3000
DATA_STORE=mysql
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=todo_user
DB_PASSWORD=强密码
DB_NAME=todo_app

生产环境不要用 root 连数据库。创建一个只对 todo_app 有权限的用户：

sql
CREATE USER 'todo_user'@'localhost' IDENTIFIED BY '强密码';
GRANT SELECT, INSERT, UPDATE, DELETE ON todo_app.* TO 'todo_user'@'localhost';
FLUSH PRIVILEGES;

用 PM2 守护进程

直接 node src/server.js，终端一关，进程就没了。用 PM2：

bash
npm install -g pm2
pm2 start src/server.js --name todo-app
pm2 save
pm2 startup

常用命令：

bash
pm2 status
pm2 logs todo-app
pm2 restart todo-app
pm2 stop todo-app

PM2 会在进程崩溃时自动重启。注意：如果你用 JSON 存储，PM2 多实例模式（cluster）会导致多个进程同时写同一个文件，写队列失效。JSON 模式只能单实例；MySQL 模式才可以考虑多实例。

Nginx 反向代理

Node.js 监听 127.0.0.1:3000，Nginx 监听 80/443，转发请求：

nginx
server {
    listen 80;
    server_name todo.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

HTTPS 用 Certbot：

bash
sudo certbot --nginx -d todo.example.com

应用里设置：

javascript
app.set('trust proxy', 1);

这样 req.ip 和 req.protocol 才能拿到真实值。

健康检查

/api/health 返回：

json
{ "status": "ok", "store": "mysql", "timestamp": "..." }

负载均衡、监控、容器编排都可以用它判断实例是否存活。更严格的健康检查会 ping 数据库，但要注意：数据库短暂抖动不应该导致所有实例被重启。通常区分“存活探针”（进程活着）和“就绪探针”（能处理请求）。

备份

MySQL 每天备份：

bash
mysqldump -u todo_user -p todo_app > backup-$(date +%F).sql

把备份传到另一台机器或对象存储。没有备份的数据，等于随时可能丢的数据。

日志

PM2 日志：

bash
pm2 logs todo-app --lines 200

生产环境建议接入集中式日志（如 ELK、Loki），至少要做到：

  • 错误日志单独文件。
  • 日志轮转，避免磁盘写满。
  • 不记录密码、Token、完整请求体。

技术讲解

用三分钟讲清楚四件事：

  1. 架构：浏览器 → Express 路由 → 业务层 → 仓库 → MySQL。
  2. 数据层设计：为什么抽仓库接口，JSON 和 MySQL 如何切换。
  3. 异步与错误处理：async/await、asyncHandler、统一错误中间件。
  4. 踩过的坑：选一个真实的，讲“现象 → 原因 → 解决 → 学到什么”。

不要念代码。评委不关心你写了多少行，关心你是否理解为什么这样写。

常见提问

问：为什么用 Express，不用原生 http？

答：原生 http 让我理解了请求、响应、路由和请求体的底层机制；Express 把重复劳动封装成路由和中间件，让代码更可维护。我先用原生写了一遍，所以知道 Express 帮我做了什么。

问：为什么用 EJS，不用 React/Vue？

答：这一版的目标是后端能力，服务端渲染能用最少的代码完成页面交互，不需要构建工具和前端状态管理。如果要做更复杂的交互，我会把页面换成前后端分离，API 已经准备好了。

问：数据层为什么要抽仓库？

答：把“容易变”的存储实现和“不容易变”的业务规则分开。JSON 和 MySQL 的切换只改仓库，路由和页面不动；测试可以用内存仓库，不依赖数据库。

问：怎么防 SQL 注入？

答：所有 SQL 用 ? 占位符，参数交给驱动转义；动态列名只来自代码白名单，不来自用户输入。

问：两个请求同时修改同一条数据会怎样？

答：当前是“后写覆盖先写”。如果要严格，可以用乐观锁（版本号）或数据库原子更新。比如 toggle 可以改成 UPDATE ... SET completed = NOT completed，避免先读后写的竞态。

问：如果继续做，你会加什么？

答：按优先级：用户登录与数据隔离、分页与排序、截止日期/优先级、自动化部署与监控、E2E 测试。每一项都能从现有架构自然扩展。

附录 B 常见错误与排查手册

这份手册按“现象 → 原因 → 解决”组织。遇到问题时，先看错误信息的最后几行，找到自己的文件名和行号，再对照这里。

B.1 Cannot find module './xxx'

现象

text
Error: Cannot find module './data'
Require stack:
- C:\project\src\app.js

原因

  • 路径写错，或者文件不存在。
  • 少了 ./，Node.js 去 node_modules 找包。
  • 文件名大小写不一致。Windows 不区分，Linux 区分。
  • 文件扩展名不是 .js / .json / .node，且没有写全。

解决

  1. 确认文件真的存在，路径相对于当前文件，不是相对于启动目录。
  2. 同目录用 ./data，上一级用 ../data。
  3. 统一小写文件名，避免跨平台问题。
  4. 清理 node_modules 后重新 npm install（少见，但依赖损坏时有效）。

B.2 EADDRINUSE: address already in use :::3000

现象

服务器启动时报端口占用。

原因

  • 之前的 Node 进程没关。
  • 其他程序占用了 3000。

解决

powershell
# Windows
netstat -ano | findstr :3000
taskkill /PID <PID> /F
bash
# macOS / Linux
lsof -i :3000
kill -9 <PID>

或者换端口：

bash
PORT=3001 npm run dev

Windows PowerShell：

powershell
$env:PORT=3001; npm run dev

B.3 Failed to lookup view "list" in views directory

现象

访问 /todos 报错，找不到模板。

原因

  • views 路径不对。
  • 文件名不是 list.ejs。
  • 没有设置 view engine。

解决

javascript
app.set('view engine', 'ejs');
app.set('views', path.join(__dirname, '..', 'views'));

确认 views/list.ejs 存在，文件名大小写一致。

B.4 req.body 是 undefined

现象

表单提交或 POST JSON 后，req.body.title 报错。

原因

  • 没有注册 express.json() / express.urlencoded()。
  • 注册顺序在路由之后。
  • Content-Type 不匹配：JSON 请求用了 application/x-www-form-urlencoded，或者表单用了 JSON。
  • 请求体为空。

解决

javascript
app.use(express.json({ limit: '100kb' }));
app.use(express.urlencoded({ extended: false, limit: '100kb' }));

// 然后再挂路由
app.use('/api/todos', todosRouter);

用 curl 测试时明确指定：

bash
curl -X POST http://localhost:3000/api/todos \
  -H "Content-Type: application/json" \
  -d '{"title":"test"}'

B.5 路由 404，但路径看起来没错

原因

  • 路由注册顺序问题：/:id 把 stats 当成了 id。
  • 挂载前缀重复：app.use('/api/todos', router)，router 里又写了 /api/todos。
  • 方法不匹配：用 GET 访问了 POST 路由。
  • 末尾斜杠：/todos/ 和 /todos 在 Express 默认配置下通常等价，但某些中间件会区分。

解决

  • 具体路由放前面：/stats 在 /:id 之前。
  • router 内部用相对路径 /、/:id。
  • 用 curl -i 看状态码，用 app._router.stack 或日志确认注册了哪些路由。
  • 开发时加一个日志中间件，打印 req.method 和 req.originalUrl。

B.6 请求一直挂起，浏览器转圈

原因

  • 中间件没有调用 next()，也没有发送响应。
  • async 路由抛错，但没有被捕获，Promise 一直 pending。
  • 路由处理函数里 await 了一个永远不会 resolve 的 Promise。

解决

  • 检查每个中间件是否有 next() 或 res.send()。
  • 给 async 路由加 asyncHandler 或 try/catch + next(err)。
  • 用日志定位最后执行到哪一行。

B.7 Cannot set headers after they are sent to the client

现象

text
Error [ERR_HTTP_HEADERS_SENT]: Cannot set headers after they are sent to the client

原因

一次请求里发送了两次响应。比如：

javascript
res.json(todo);
res.status(500).json({ error: '...' }); // 又发了一次

或者 try/catch 里已经 res.json，catch 又 res.json。

解决

  • 确保每个分支只发送一次响应。
  • 发送后 return：
javascript
if (!todo) {
  return res.status(404).json({ error: '待办不存在' });
}
res.json(todo);
  • 错误中间件里检查 res.headersSent。

B.8 JSON 文件损坏：Unexpected token / DATA_FILE_INVALID

现象

启动或读取时报 JSON 解析错误。

原因

  • 手动改文件时少了逗号、引号、括号。
  • 写入过程中断，文件只写了一半。
  • 文件是空文件（JSON.parse('') 报错）。

解决

  1. 打开 data/todos.json，用 VS Code 的 JSON 校验看红波浪线。
  2. 修复 JSON，或者备份后删掉，让程序生成空数组。
  3. 确认写入用了临时文件 + rename，避免半截文件。
  4. 生产环境用数据库，不要用 JSON 文件承载重要数据。

B.9 重启后数据没了

原因

  • 还在用内存仓库，没有切换到 JSON/MySQL。
  • JSON 文件路径不对，每次写到不同位置。
  • 写操作没有 await，进程退出时还没写完。
  • 数据库没提交（MySQL 默认自动提交，一般不会）。
  • 用了 PM2 cluster 多实例，各自写不同文件/内存。

解决

  • 确认 DATA_STORE 和 DATA_FILE。
  • 打印 config.jsonFile 的绝对路径，确认文件真的在那里。
  • 所有仓库写操作都要 await。
  • JSON 模式只跑单实例。

B.10 ER_ACCESS_DENIED_ERROR

现象

text

原因

  • 密码错。
  • 用户名错。
  • 用户没有从该主机连接的权限。
  • MySQL 8 认证插件不兼容旧客户端。

解决

  • 检查 .env 的 DB_USER / DB_PASSWORD。
  • 用命令行验证：
bash

  • 确认用户权限：
sql
SELECT user, host FROM mysql.user;

原因

解决

B.13 时间差了 8 小时

原因

  • 数据库存的是本地时间，代码按 UTC 解析，或者反过来。
  • 连接没有设置 timezone: 'Z'。
  • 混用了 NOW() 和 UTC_TIMESTAMP()。

解决

  • 统一存 UTC：UTC_TIMESTAMP(3)。
  • 连接池设置 timezone: 'Z'。
  • 展示时用 toLocaleString('zh-CN') 转本地时区。
  • 不要在不同地方混用两种时间函数。

B.14 中文乱码

原因

  • 响应头没有 charset=utf-8。
  • HTML 没有 <meta charset="UTF-8">。
  • 数据库/表不是 utf8mb4。
  • 连接没有设置 charset: 'utf8mb4'。
  • 终端编码不是 UTF-8（Windows 旧版 CMD 常见）。

解决

  • API：res.json() 会自动设置 JSON 的 charset；手写 res.writeHead 时要加。
  • 页面：<meta charset="UTF-8">。
  • 数据库：
sql
ALTER DATABASE todo_app CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
ALTER TABLE todos CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
  • 连接池：charset: 'utf8mb4'。
  • Windows 终端：
powershell
chcp 65001

B.15 页面弹出 alert(1)：XSS

原因

用了 <%- 输出用户内容，或者用 innerHTML 插入未转义的数据。

解决

  • EJS 一律用 <%=。
  • 前端插入文本用 textContent，不要用 innerHTML。
  • 富文本用 sanitize-html 白名单过滤。
  • 设置 CSP 作为纵深防御。

测试：

text
/todos?error=<script>alert(1)</script>

如果弹窗，说明有 XSS。

B.16 npm install 失败

常见错误

  • ETIMEDOUT / ECONNRESET：网络问题。
  • ERESOLVE：依赖版本冲突。
  • EACCES：权限问题。
  • 404 Not Found：包名或版本写错。

解决

bash
npm config get registry
npm cache clean --force
npm install

国内可临时换镜像：

bash
npm config set registry https://registry.npmmirror.com

依赖冲突时，先看错误信息里是哪两个包，再决定升级/降级，不要直接 --force。

B.17 测试端口冲突 / 测试互相影响

原因

  • 测试里硬编码了 3000 端口。
  • 多个测试文件共享同一个数据文件。
  • 测试没有清理临时目录。

解决

javascript
const server = app.listen(0); // 随机端口

数据层测试用 fs.mkdtemp；API 测试用内存仓库。每个测试文件独立，测试之间不共享可变状态。

B.18 .env 被提交到 Git

解决

  1. 立刻把 .env 从 Git 历史移除（git rm --cached .env，必要时用 git filter-repo）。
  2. 更换所有泄露的密码/密钥。历史里的东西删掉也可能已经被拉取。
  3. 把 .env 加入 .gitignore。
  4. 提交 .env.example 作为模板。

不要只是“删掉文件再提交”，旧提交里仍然有密码。

B.19 部署后页面样式丢失

原因

  • express.static 路径不对。
  • Nginx 只转发了 API，没有转发静态资源。
  • href="/styles.css" 写成了相对路径。
  • 生产环境缓存了旧版本。

解决

  • 确认 public/styles.css 存在，app.use(express.static(...)) 在路由之前。
  • 浏览器开发者工具看 /styles.css 的响应状态码。
  • 强制刷新或清缓存。

B.20 排查问题的通用步骤

  1. 读错误信息的最后一行。 那里通常有错误类型和消息。
  2. 找自己的文件名和行号。 忽略 node_modules 里的栈。
  3. 缩小范围。 是启动就错，还是请求才错？是所有请求，还是某个接口？
  4. 加日志。 在关键分支打印输入、输出、执行到哪一步。
  5. 做最小复现。 新建一个最小文件，只保留出错的几行，排除其他干扰。
  6. 对比已知可用的版本。 git diff 看最近改了什么。
  7. 搜索错误信息。 去掉路径和变量，搜核心错误文本。
  8. 问人时给出完整信息。 操作系统、Node 版本、命令、完整错误、相关代码、已经试过什么。

记住：错误信息不是敌人，是线索。 越早学会读它，进步越快。

C.11 给教师的教学提示

  1. 每节课开始先检查上次的成果。 不用点名，举手统计即可。没完成的，课后补。
  2. 演示要“故意犯错”。 比如漏 await、写错路径、拼接 SQL，让学生看到错误信息和修复过程。只看正确代码，学不会调试。
  3. 巡场比讲授重要。 学生卡住的地方，才是真正需要讲的地方。
  4. 不要替学生改代码。 指出错误位置，让他自己改。你改一次，他下次还会错。
  5. 每组必须有一个能运行的项目。 不能运行的项目，不进入答辩。
  6. 把 README 当成交付物。 从第 6 次课开始，每次更新；不要到最后一天补。
  7. 控制范围。 学生总想加登录、加地图、加 AI。告诉他们：先把 P0 做完，再加 P2。
